# Changelog

## Unreleased

The relay bot's advisory reads for new candidates take turns (ai-tools-alerts#vszx). Each run may ask GitHub's advisory database about ten candidates. It asked in the order of the collector's record, which is the same every hour, so the first ten candidates whose vendor page confirmed them were read on every run and the others never: 24 of 34 on the live poster, on every run since 0.3.0. A candidate never read is rated from its vendor page alone. A level its advisory's fields support (a reviewed weakness, a malware entry) was never reached, and a post made from it carried no claim. Now each run reads every candidate's vendor page first, as before and in the same order, and then asks for the advisories from where the last run's requests ended: with n candidates and ten requests a run, every one is asked for within ceil(n / 10) runs. A slow or failing API, a missed run and two runs in one hour change nothing about that: the next run goes on from the last id a request was made for. Which candidates are admitted, their order, and the pages fetched are unchanged.

What an operator should know. The poster writes one more file beside the ledger, `<ledger>.admit-turn.json`, holding the last advisory id asked for. If it is lost or does not read, the turn starts again at the first id, and a run that cannot write it says so on stderr and goes on. An earlier poster ignores the file, so a rollback is installing the earlier release; no ledger, journal, wire format, schema, manifest, ruleset or scope file changes. The line `advisory reads: N id(s) not read this run` now names the ids (the first 40), so two runs' lines show the turn. On the first runs after install, candidates that were never read are read: one whose advisory supports more than its alert's level is raised under the existing rules, and a held notice whose advisory supports a level posts. Expect those in the first ceil(n / 10) runs and none after them.

Not changed: alerts first posted under an id of the form `GHSA-...:owner/repo` (the MCP Inspector and MCP TypeScript SDK alerts of 2026-11-07) are read by no lane, because neither the relay bot nor a member's check reads an id with a slash after the colon. Their level is not recomputed.

## 0.5.0 — 2026-11-28

Corrections to grouped alerts, per-channel level replies, a fuller read of an advisory's package box, and the member's reading of a current Hermes release. A channel that refused a level reply is sent the thread's standing level again (ai-tools-alerts#aqtf). Retracting one advisory of a grouped alert or of a held grouped notice no longer hides or drops the others (ai-tools-alerts#z360, ai-tools-alerts#9je7), and an advisory that still supports a grouped alert's level leaves it when the first advisory is withdrawn or lowered (ai-tools-alerts#yd1y). The relay bot reads every package, range and patched version of a repository advisory (ai-tools-alerts#xkbf). The member's CLI reads the release a current Hermes runs (ai-tools-alerts#1qy4). No wire format, schema, manifest, ruleset or scope file changes, so the trust root, the ruleset pin and the checkpoint key certificate stay as they were; `spec/wire.md` changes in prose only. The poster's ledger and journal gain keys an older poster refuses (`lacks`, `copied`, `uneven`, `split`, and a journal item's `again`). Going back is possible only under the conditions each entry below names, and otherwise goes forward.

A level reply that one channel refused is no longer lost to that channel (ai-tools-alerts#aqtf). A critical alert has a thread in two channels and every level reply goes to both. The poster gives up a reply a channel refused twice, three days apart, and until now nothing remembered which channel lacked it: a raise that one channel never took left the alert low there for good, a lowering left it high, and a withdrawal left it shown.

- **The ledger names the channel.** For each thread it records which channels have not taken the thread's standing level reply, the last one any channel acknowledged. A run sends such a channel that reply again when nothing of the thread is in flight: the withdrawal, or the thread's level alone. A channel that shows less than the thread stands at is served before the run's lowerings, a channel that shows more after them.
- **The pace is the journal's.** Refused, the reply waits three days, is sent once more, is given up and is planned again by the next run, for as long as the relay refuses it. Such a refusal does not count toward the two that stop a run. Each reply given up is counted in the next daily digest as before.
- **A thread withdrawn in one channel only** is what its standing reply says. One that left the state in one channel is at its level again: renewed, stepped down, copied and judged like any other, where until now it got no renewal and no new wait. One whose withdrawal a channel never took stays withdrawn, and that channel is sent the withdrawal.
- **The checkpoint** leaves out the root of a channel that lacks the standing reply until the channel takes it, as it already did while the reply waited in the journal.

What an operator should know. No wire format, schema, manifest, ruleset, scope file or CLI change: the replies are the ones the poster already sends. A ledger entry may now hold `lacks` (the channels that lack the standing reply, each with the level or state it stands at), `copied` (a root posted in a second channel ahead of the reply that raises the thread) and `uneven` (a reply was sent again to one channel; claims on that thread then name its first id only), and a journal item may hold `again`. `lacks`, `copied` and `again` are gone after any run whose sends were all acknowledged; `uneven` stays. An older poster refuses a ledger or a journal that holds any of them, so revert only while none is on disk, and otherwise go forward. When a thread leaves the withdrawn state and one channel never took the withdrawal, that channel is now sent the level reply too.

What this does not cover: a reply with no level (a fix, a range) that one channel refused twice is still lost to that channel; a send whose outcome is unknown is settled as before, and one the mirror never shows is sent again after one to three days.

The relay bot reads every package, every range and every patched version of a repository advisory (ai-tools-alerts#xkbf). GitHub prints a package with several ranges as one row, each range and each patched version in its own element under one label, and prints the labels in the first row only. The poster read one range, then looked for the "Patched versions" label, and read no row without labels. So the catalog notice for GHSA-v2gx-m79c-pvxj (`@modelcontextprotocol/inspector`, 2026-11-27) said `>=2.0.0,<=2.16.0` and no fix, where the advisory also states `<= 1.0.6` and the fixes 2.17.0 and 1.0.7: a member on 1.0.x was not matched and a member on 2.x was told of no fix. A product named only in a later row was not matched at all. Now the package box is read by its rows and columns. An advisory with several ranges for one product posts the highest patched version as the fix and no range ("see the source"), as an advisory with several blocks always did; a member on a patched release of an older branch is matched and told the highest fix, which is wider than the advisory and the safe direction. A fix read where none was read before can raise a level under the existing rules. A package box in a shape the poster does not know is not read in part: the advisory waits and the run counts it under "advisory page not parsed, deferred" (its end state is ai-tools-alerts#psb5). Poster only; no wire format, schema, manifest, ruleset or scope file changes; a rollback is a revert. Notices already posted keep their values: nothing reads a catalog notice again (ai-tools-alerts#n2yj).

Retracting one advisory of a grouped alert no longer hides the others (ai-tools-alerts#z360). Since ai-tools-alerts#faxq one relay-bot post covers every advisory of a product that one release fixes. A reader hides a post when any id it carries is in the trust manifest's `retracted` list, so retracting one advisory hid the rest, which are still true, and the relay bot never posted them again. Readers are unchanged: they cannot tell one advisory's CVE from a second advisory in the same post, and hiding by every id is what keeps a stolen key from escaping a retraction by dropping an alias.

- **The relay bot posts the others again.** Each run reads the manifest from its own copy of the mirror (as its last pull left it; the daily digest pulls it). For a post readers hide because of the manifest, and not a curator's retraction, each other id is checked once against its own repository advisory page. An id whose page assigns no retracted id is released from the hidden post and posted in a new one, grouped by fix with the other released ids, at the level their own sources give. An id whose page assigns a retracted id (the retracted advisory's own CVE) stays with the hidden post. An id no source confirms stays too: on doubt the retraction wins. An id no page could be read for is tried again next run. A post hidden only by an alias a curator added is left as it is. An advisory that joined the hidden post by its fix (ai-tools-alerts#btqg), and so was never named in it, is judged the same way. A released advisory is not old news: the seven-day age limit does not demote it. If the manifest later stops retracting the advisory, the old post shows again beside the new one; both are true.
- **Nothing retracted is planned.** An advisory any of whose ids the manifest retracts starts no post.
- **Grouped notices too (ai-tools-alerts#9je7).** A grouped notice waiting for the weekly summary used to be dropped whole when one of its advisories was retracted, and the others were marked as already counted. Each run now judges the notice's other ids the same way, by each one's own advisory page: a proven one is held as a notice of its own and counted by the next weekly summary; the retracted advisory and its own CVE are dropped. The digest neither counts nor drops such a notice until a run has judged it. No state format change.
- **Operators.** The ledger entry of such a post holds `split` (the ids released and kept). An older poster refuses that ledger: revert only while no entry holds `split`. No wire format, schema, manifest, ruleset or CLI change.

The CLI reads the release a current Hermes runs (ai-tools-alerts#1qy4). Since Hermes 0.23, its `pyproject.toml` says 0.0.0, and the CLI read that as no version, so every Hermes alert was "may apply" on a current install and none interrupted. Now the version comes, in order, from the install stamp (`~/.hermes/hermes-agent/install-stamp.json`, at most 64 KiB), from `pyproject.toml` when it names a real release, or from a stable release tag (`vX.Y.Z`) on the checkout's HEAD, read with `git tag --points-at HEAD`. `hermes` itself is never run, since `hermes --version` checks for updates over the network. Only an exact release counts: a stamp must say distance 0 and not dirty, and in a git checkout name the commit at HEAD. A checkout between releases, such as one tracking `main`, still has no version and its matches stay "may apply", because the nearest earlier release would hide an advisory whose range starts after it. Every `git` the CLI runs now runs without the caller's `GIT_*` variables, never fetches and never prompts. No wire format, schema, manifest, ruleset or scope file changes; a rollback is a revert.

An advisory in a grouped alert keeps its alert when the group's first advisory is withdrawn or lowered (ai-tools-alerts#yd1y). A grouped alert's level rests on its first advisory, the one a member's source check reads. When that advisory was withdrawn, or came to support less, while another advisory in the group still supported the level, the member's check stopped confirming the alert, and the relay bot could neither lower it (the other advisory kept it unjudged) nor say that the other advisory still stood. Now, in a run that reads the first advisory's sources whole, the relay bot reads each other advisory's own response. Each one that supports more than the first advisory's sources state leaves the alert, and the next run posts those that left as a new alert, grouped by fix, at the level their own sources give, under an id a member's check reads. When every other advisory has left, the old alert is judged by its first advisory alone and is lowered or withdrawn under the usual rules: the lower state held for 24 hours, seven quiet days. Its text still lists the advisories that left.

- **What stays as it was.** An advisory whose own response cannot be read, or is not a reviewed or vendor advisory, stays in the alert. So does one that supports no more than the first advisory does, and an id whose own page assigns one of the alert's first advisory's ids (a vendor's GHSA beside its CVE: the same advisory, recorded as `kept`). While any of these stays, the alert stays unjudged: if its first advisory supports less than the alert's level, it steps down after 44 days without a confirming read (ai-tools-alerts#759h). The old alert of a group held at its level by the vendor's prose stays at that level after the others leave.
- **Also when an advisory comes to say more.** An advisory in a grouped alert whose own source comes to support more than the alert's first advisory leaves the same way and is posted at its own level; before, the alert stayed at the first advisory's level and the higher one was never posted.
- **If the first advisory comes back.** There are then two alerts, the old one and the new one. Both are true.
- **If an advisory that left is later retracted.** The old alert still names it, so readers hide the old alert too. The relay bot then posts the old alert's first advisory again, as it does for any retraction in a group (ai-tools-alerts#z360).
- **Operators.** The leaving advisories are recorded in the ledger entry's `split`, as for a retraction above. On the first run after install, each open grouped alert already in this state releases its advisories, reading at most ten new advisory pages a run; each alert takes its turn within as many hours as there are open alerts. No wire format, schema, manifest, ruleset or CLI change.

## 0.4.0 — 2026-11-28

Relay-bot alerts now expire unless renewed, end 90 days after their last level change, and can be withdrawn; a post signed with the relay bot's key that the poster did not send is left out of checkpoints. The relay bot puts its claim on each new root a reading supports (a root without one never expires, as before), renews a claimed thread while its source confirms it, steps down a level nothing has confirmed for 44 days, stops renewing a thread 90 days after its level last changed, and sends the withdrawal when every source of a thread states it (ai-tools-alerts#gtw9, ai-tools-alerts#65xv, ai-tools-alerts#kk2q). Its checkpoint is dated when signed, lists a renewed thread in a few events, and leaves out any relay-bot post the poster did not send (ai-tools-alerts#p93w, ai-tools-alerts#m729, ai-tools-alerts#9cch). A later advisory one release fixes joins the open alert of that fix, and threads under a former product name are judged like any other (ai-tools-alerts#btqg, ai-tools-alerts#aabw). The member's CLI puts a poster key on probation after two unsupported alerts in seven days, no longer lets a thread's aliases keep it unjudged, and flags a `fixed` version its advisory does not state (ai-tools-alerts#cftg, ai-tools-alerts#nx25, ai-tools-alerts#53fy). No wire format, schema, manifest, ruleset or scope file changes, so the trust root and the ruleset pin stay as 0.2.1 left them. The source check's cache is rebuilt once (version 7). The poster's ledger and journal gain keys an older poster refuses (`claim`, `withdrawn`, `ended`, `joined`, and a digest that carries `foreign`); the sent record beside the ledger is a new file an older poster ignores. Going back is possible only under the conditions each entry below names, and otherwise goes forward.

Alerts now expire unless their source keeps confirming them (ai-tools-alerts#gtw9, the poster half of ai-tools-alerts#r0ra; `spec/wire.md` "The claim"). A root the relay bot posts carries its claim, so readers 0.1.8 and later compute that thread's life: critical for 14 days after the last confirmation, high to day 30, notice to day 90. The poster renews each such thread before half of that has run: a reply with no block, "Sources checked. No change to this alert.", with the claim in its event tag, confirmed at the run's time when the source still states the level. When the source cannot be read (a 403, an outage) the renewal keeps the last confirmation and a new check time, which holds the level for up to 45 days. A day before that ceiling the poster lowers the thread one level and says why in the reply ("No source has confirmed the higher level for 44 days."); the next step follows when the new level's own time runs out, and at notice the thread leaves readers 90 days later. A source that confirms again renews it, and one that supports more raises it. Threads posted before this change carry no claim on their root and are untouched: they are never renewed and never expire. Readers 0.1.4 to 0.1.7 ignore all of it and keep every alert at its highest level.

The checkpoint never lists a thread's root without the renewals that keep it standing. A renewal the mirror stops serving is no longer given up after 72 hours while the root is still listed; its thread is left out of checkpoints until that renewal or a later one is served, as a curator's missing correction already is. Before it signs, the poster reads its own copy of the mirror as a reader would and leaves out every claimed root whose renewals no longer hold the level the bot last named above notice, whatever the cause: a renewal it could not deliver, a channel that lacks a level change another channel has, a lost ledger or state file. A thread that must be listed and does not fit a checkpoint whole brings its newest renewals. A thread a checkpoint does not list keeps its level on every reader.

What an operator should know. The poster must keep running: from the first root posted after this update, a poster that signs checkpoints and cannot post for seven days lets its criticals fall to high on readers 0.1.8 and later (a poster that is stopped signs nothing, and nothing expires). The summary line gains `renewed=N` (`N/M` when M sends were not acknowledged) in a run that tried a renewal. A renewal is not journaled and never appears in `pending`. If the checkpoint state file is lost, the next runs renew every such thread once, whatever its age. Rollback is forward only once a root has been posted with a claim: the ledger then holds `claim` and `root_ids` in that thread's entry, a root's or copy's journal item holds `claim`, and an owed entry of the checkpoint state may hold `renewal`, and an older poster refuses each of them. Before that, revert the merge. Not built here, each in its own issue: the 45 days as a key of `spec/ruleset.json` (it waits for the next ruleset version), the checkpoint dated when it is signed, and a rule for when a thread whose source keeps confirming stops being renewed (each open high adds 24 events a year to the feed file).

An advisory that a release already announced fixes no longer gets an alert of its own (ai-tools-alerts#btqg). Since ai-tools-alerts#faxq, advisories for one product that one release fixes are one alert when one poster run sees them together. One seen in a later run still posted its own alert, telling members again to make the upgrade they were already told to make. Now it joins the open alert of that fix. The poster keeps the newcomer's ids with that alert and lists its sources, and sends no reply unless the alert's range must widen to cover the newcomer: then one reply states the wider range. A join never raises an alert or marks it exploited. Its level rests on its first advisory, which a member's source check reads and which says nothing about the newcomer. So an advisory that alone rates higher, or that KEV lists where the alert has no listing, posts its own alert as before. The newcomer's ids are never published in the alert, so the same holds later: when the newcomer's own source comes to rate it higher, KEV lists it, or its vendor moves its fix past the alert's, it leaves the alert and posts its own. Advisories that join together leave one at a time. Other cases that post their own alert as before:

- the alert of that fix is withdrawn, or the mirror shows it retracted or expired;
- one of the newcomer's ids is retracted;
- the poster cannot read the mirror that run;
- the alert already holds 51 ids with the newcomer's;
- the newcomer's own advisory could not be read that run;
- the alert is filed under a former name that several products share.

A newcomer waits while the alert has a send in flight, and joins in the run after that send is settled. Operators: the ledger entry of a joined alert holds `joined`, the ids of each advisory that joined it, and an older poster refuses that ledger. Going back: with no poster run in progress, `jq 'del(.entries[].joined)' ledger.json > ledger.json.new && mv ledger.json.new ledger.json` in the ledger's directory. The older poster then reads a joined newcomer's ids as the alert's own: it never posts an alert for the newcomer, and a later sighting of the alert's first advisory can narrow a range the join widened. No wire format, schema, manifest, ruleset or scope file changes.

A member's CLI puts a poster key on probation after two alerts its own source check found unsupported (design review of 2026-11-23, finding D14, the member half; ai-tools-alerts#cftg; ai-tools-alerts#m729, below, is the poster half). Until now each fabricated alert was limited on its own: unread it interrupted as one of two unverified alerts per key per day, and once read it showed at notice. Nothing limited the series, and a lowering the member could not check still applied after 72 hours. Whoever held the relay-bot key kept both for as long as the key stayed in the manifest, which only a person can change.

- **Two strikes in seven days.** An alert is a strike once the CLI's reads have found that no source ever supported one of its products (the test that already shows such a match at notice). Copies of one advisory are one strike, and so are two products of one alert; two alerts under one id whose content differs are two. Not a strike: a critical the source supports at a lower level, an alert whose support was read earlier and is gone, a failed read, an alert never read, a curator's alert. A strike is written down and stands seven days whatever happens to its thread.
- **Thirty days of probation, on that machine.** The key's alerts that the CLI has not confirmed are held: listed by `check` with their own line, in `held_critical` of `run --json`, no notification, no exit 2. An alert the CLI confirms from its source interrupts as before. The key's lowerings and narrowings do not apply after 72 hours; only the CLI's own confirmation applies them, and one that had applied unchecked stops applying. A reply signed by the key that lowers another relay-bot key's alert is treated the same way.
- **It ends by itself.** After 30 days the held alerts take the free slots, and the 72 hours of each lowering start at the first checkpoint issued after the end that the machine holds. A key with two strikes in the last seven days at that moment starts a new probation. `check` prints one line per key on probation with the time it ends.
- **The record.** `unverified.json` gains `probation`. A record without it loads as before. An earlier CLI that reads the newer record treats it as damaged and starts it again, as it does for any shape it does not know: the waits and the memory of support start over.

What this does not cover. An alert the CLI never reads earns no strike: with `verify = "off"`, or with the sources out of reach, only the cap of two a day applies. A damaged record loses a running probation. With more than one relay-bot key in the manifest (there is one), a strike and a held alert count against the key that started the thread, so a key on probation could still add to or raise another key's thread (ai-tools-alerts#ex8f). A real key whose alerts a member's sources twice fail to support goes on probation on that member; its confirmed alerts still interrupt.

The poster leaves out of its checkpoint any relay-bot post it did not send (design review of 2026-11-23, finding D14, ai-tools-alerts#m729). The key that signs alerts exists on more than one machine; the checkpoint key exists only on the poster. Until now the poster's checkpoint listed every post on the mirror signed with a key the manifest names, so a post made with a stolen relay-bot key reached every member under the poster's own signature. Revoking the key takes the trust root and a person. This takes neither.

- **Written down before the send.** With `checkpoint_key_file` set, the poster records the id of every event it signs in `<ledger>.sent.json` (a lock file, `<ledger>.sent.json.lock`, sits beside it) before a byte of the request is written. A record that cannot be written means the post is not sent in that run.
- **Left out of the checkpoint.** Each run compares the relay-bot posts in the alert channels of the poster's copy of the mirror with the record. A post that is not in it is in no checkpoint, and when it starts a thread, neither is any reply to it. It counts for nothing the poster decides about real threads: it renews none, lowers none and makes no real renewal redundant. The CLI from 0.1.6 on applies only what a checkpoint lists, so it never shows the post. The summary line's `checkpoint=` field gains `,foreign=N` while N such posts are on the mirror; signing goes on.
- **Said once.** The next daily digest ends with one line, in English and in the Japanese copy: "Warning: an event signed with this service's key was not sent by this service. No checkpoint lists it, so the CLI does not apply it." It names no id, and is said again only for a new post or for one that left the mirror and came back.
- **How the record starts.** On the first run, and after a lost or unreadable record, the poster takes as sent what the checkpoint the mirror serves under its key lists (only while that checkpoint is fresh, so an old one served again counts for nothing), what the ledger and the journal record, and the posts still owed. It takes nothing because the mirror serves it, so losing the file never brings back a post that was left out. After a loss, an old Japanese reply, renewal or digest that none of the three holds reads as foreign: it is left out and the digest says the line once.
- **Unknown sends are settled by id.** With a checkpoint key, a send that got no answer is matched on the mirror only by an id in the record. Its text is no longer enough, since anyone with the key can sign the same text again. Without a checkpoint key nothing changes.
- **Left out of the poster's other reads (ai-tools-alerts#9cch).** With a checkpoint key, every other read the poster makes of its copy of the mirror leaves the same posts out: settling a send, the withdrawn list behind the digest and the copies, and the translation of a curator's posts. A forged `lang: ja` reply no longer marks a curator's post as translated, a curator's reply in a forged thread is not translated, and a forged reply in a real thread changes nothing in the advisory text a curator's amendment is translated from. That translation does not run until the record has been started (`translate=no-record` in the summary). The record is started at the end of the first run that reaches its checkpoint step with a mirror it can read and a certificate that names its key, and the run after that translates; a poster that says `checkpoint=no-certificate` or `checkpoint=no-mirror` every run does not translate until that is mended. The same after a lost record, and a record lost in the middle of the pass translates nothing in that run.
- A post that is no longer served is dropped from the poster's stored copy, and a run whose pull finds the store full removes such posts and pulls once more, so they cannot keep the store at its limit.

What an operator should know. Install it between runs, while `aitools-alerts-poster pending` lists nothing: a send whose outcome is unknown at that moment has no id in the record, is never settled, and is sent again after one to three days; its first copy, if the relay took it, is left out. Going back: an older poster ignores the two new files and refuses a journal whose digest item carries `foreign`, in `outbox` or in `withheld`; revert when neither holds a digest. No wire format, schema, manifest, ruleset or CLI change.

What this does not cover: whoever holds the checkpoint key and the relay-bot key together; a CLI older than 0.1.6, which knows no checkpoint; the poster's other reads of its mirror copy (the digest's list of withdrawn threads, the level recompute and the curator-translation pass still read such a post; ai-tools-alerts#9cch); a key holder who fills the mirror's own capped files (ai-tools-alerts#pdag for the poster's side of it). The member's half of the finding, a key on probation after two unsupported alerts, is ai-tools-alerts#cftg.

An alert posted under a product's earlier name is now corrected from its source like every other alert (ai-tools-alerts#aabw). A thread keeps the name it was posted under, and four names the scope file lists as `formerly` still carry threads: "MCP servers and clients", which seven MCP servers had, "MCP Inspector", "MCP TypeScript SDK" and "MCP Python SDK". Until now the relay bot did not recompute such a thread, so it was never lowered when its advisory was withdrawn and, since 0.3.0, was stepped down after 45 days whatever its source said; and a member's source check answered "unknown" for it. Now both read the name by one rule, the one a signed claim was already computed by: a former name stands for every product whose scope entry lists it, and what the thread's own advisory supports for any of them is what it supports for the thread. One thing differs from a current name: "MCP servers and clients" once matched any MCP server, so a thread under it may be about a server that is none of those seven, and an advisory that names none of them says nothing about the thread. Such a thread is unknown to both, as before: it is not lowered, and no member is told its source does not support it. The relay bot raises such a thread in the first run that reads more, lowers it, or withdraws it when its advisory is withdrawn (ai-tools-alerts#kk2q, below), under the rules every lowering follows (every source read whole, the lower level held for 24 hours, seven quiet days, the circuit breaker), and renews it with a new confirmation while its source states the level. A member's check confirms or contradicts its level from the same response, so a lowering of such a thread applies at once when the source confirms it, an alert its source never supported is shown at notice, and the `source check:` lines name it by the former name as the scope file spells it. What does not change is which installations interrupt: an installation matches such an alert by the key its MCP server is configured under, which says nothing about its package, so a match on a former name is still one the check cannot judge. It is listed with "cannot judge: no interrupt" on a reader with the pinned ruleset, as before, and its `source_check` in `--json` stays "unknown".

What stays as it was: a narrowing of such a thread is not settled by the source check. A reader of an earlier release still answers "unknown" for these threads. The source check's cache is rebuilt once more (version 7; ai-tools-alerts#nx25, below, made it 6), because the answer it stored for such a thread is one it never reads again. The scope file is checked for one more thing when it loads (entries that share a former name share ecosystem, class and authority), which the shipped file meets. No wire format, schema, manifest, ruleset or scope file changes, and the poster's ledger and state files are unchanged; a rollback is a revert.

The relay bot sends the withdrawal (ai-tools-alerts#kk2q, the poster half of ai-tools-alerts#y484; `spec/wire.md` "A withdrawal"). Until now an advisory its source withdrew lowered its alert to notice and stayed there. Now, when every advisory reading of the thread states the withdrawal, nothing supports the product, no KEV entry lists it and no reading of prose gave it more than notice, the thread gets one reply in each of its channels, `The source withdrew this advisory.` with the block `{"level":"withdrawn"}`, under the rules of every lowering: whole reads, 24 hours, seven quiet days, the circuit breaker. A CLI from 0.3.0 hides the alert when its own source check confirms the withdrawal and otherwise reads it as a lowering to notice after 72 hours. The advisory published again brings the alert back in the same thread, by a level-only reply in the run that reads it (the run after the one that sent the withdrawal, at the earliest). An unreviewed advisory outside the vendor's repository still moves nothing, withdrawn or not.

- **What older CLIs see.** Releases 0.1.4 to 0.2.1 skip the reply and keep the alert at its level. For 0.1.8 to 0.2.1 that is a change: the poster used to lower such an alert to notice for them. Sending that notice first would make the withdrawal unconfirmable on every member, since a notice that rests on a withdrawn reading has no claim of notice to carry.

The checkpoint keeps listing it, so it leaves readers as its last confirmation ages: 90 days at most.
- **An alert that returned to notice because its advisory stopped naming the product** cannot be hidden by a later withdrawal: members read that one as a lowering to notice after 72 hours.
- **Operators.** No wire format, schema, manifest, ruleset or scope file changes. The ledger entry of a withdrawn thread holds `withdrawn` (the channels that carry it), and the recompute state may hold `withdrawn` as a wait's or a reported lowering's level. An older poster refuses that ledger and starts that recompute state over. It does not refuse a withdrawal that is still in the journal: it would send the reply and record it as an ordinary one, and nothing would then end it on readers. So revert the merge only while all of this holds, and otherwise go forward: no ledger entry holds `withdrawn`; no `text` in the state file ends in the block `{"level":"withdrawn"}`, neither in `outbox[]` nor in `withheld[].items[]` (a refused reply waits there, inside its group); and the ledger's `pending` list names no key containing `#level:` (a pending record holds a key and no text, so a level reply in flight may be a withdrawal). The aliases of a relay-bot alert can no longer keep the member's source check from judging it (ai-tools-alerts#nx25). For an alert whose first id is a CVE, the check read at most three of the GitHub or OSV advisories listed as aliases, and called the read incomplete when there were more or when one failed. An id that does not exist answers 404, which was a failed read. So a post with four aliases, or with one invented one, stayed `unknown` for good: never confirmed, never contradicted, never shown at notice, and an unverified interrupt inside the cap.

- **A 404 is an answer.** The source has no such entry. It supports nothing and lowers nothing. A critical on a CVE that CISA lists for another vendor's product is contradicted in the first run when it lists one invented alias, and in the second when it lists four.
- **An alias holds the alert only until the source has answered for it.** The CLI remembers per alias when it last asked and what kind of answer came. Aliases are asked longest untried first, three new ones a run. At most eight count: the first your CLI saw the alert list, whatever later replies add or in what order. An answer stands while the last request for the alias got one; when a later request fails, the alert is `unknown` again until the source answers. A grouped alert with more than three advisories is judged once each has answered.
- **Support your CLI has read is read again in the run that judges.** An alias that is an advisory with the say and names the CVE must be read whole in that run, all of them, up to eight. A failed read of one, a 404 included, leaves the alert `unknown`.
- **An answer your CLI cannot use stops counting after 24 hours.** An entry that is too large or of a form the CLI does not read holds the alert `unknown` for 24 hours from the first incomplete read of that CVE, whatever replies the alert gets in that time, and is then left out. An alias your machine cannot reach at all (a timeout, a rate limit, a server error) is never left out: the alert stays `unknown`, as before.
- **A lowering is checked as before.** For a published lowering, retraction or withdrawal every listed alias counts, at most three, each read whole in one run, and a 404 is a failed read. Its result is kept apart from the result of a post with the same content. A narrowing is confirmed only on reads that are whole by that same rule.

What an operator should know. The source check's cache is rebuilt once (version 6); it gains `tried`, `since` and `counted`. A thread with tied aliases can take up to nine of a run's ten requests when it is read. No wire format, schema, manifest, ruleset or scope file changes. The poster dates its checkpoint when it signs it (ai-tools-alerts#p93w, from the review note on ai-tools-alerts#r0ra). Until now a checkpoint carried the time its run began and listed the posts of that run, each dated after it, so a reader held the claim of every new post back for one checkpoint. A post of the run stays owed for that run's checkpoint as before, so a crowded checkpoint is still refused rather than signed without it. The date is never raised to a post's date: after a clock set back, that would date the checkpoint ahead of the true time, which readers refuse.

A reader does not refuse a checkpoint that lists an event dated after it. This is what releases 0.1.8 to 0.3.0 do, now stated in `spec/wire.md` and tested on each of them: the event is admitted, its claim waits for a checkpoint dated at or after it, and the thread keeps its level meanwhile. The state file was the only memory that the relay had acknowledged the reply, and the renewal sent after a loss does not replace it when no source confirms. The times come from the ledger. What an operator should know. Checkpoints are dated up to a few minutes later than before. No state file, ledger, wire format, schema, manifest or ruleset changes shape, so the 0.3.0 poster reads what this one writes.

A relay-bot `fixed` version the advisory does not state no longer sends anyone to it (ai-tools-alerts#53fy, the widening half of ai-tools-alerts#swfe). After a flag, a later read that fails shows the version again until the next whole read.
- No wire, schema, manifest, ruleset or cache change. Released CLIs show the alert exactly as before.

An alert now ends, and a checkpoint lists a renewed thread in a few events (ai-tools-alerts#65xv; `spec/wire.md` "The claim"). Since 0.3.0 a thread whose source confirms it was renewed for good: a reply in each of its channels every 7 to 45 days. A checkpoint lists 990 events and listed a thread whole or not at all, so at one new alert a day most threads would have been left out of the checkpoint within months, pinned at their level on the readers that had them and hidden from new members; a reader's store of 20,000 events would have filled within two years.

- **A checkpoint lists a thread without the renewals another makes redundant.** The root, every reply that is more than a renewal, the newest renewal and the thread's newest event. The signer checks each such set with the reader's own code and lists the thread whole when a reader would build anything else from it. A thread with an owed reply or a curator's reply that does not fit whole was listed as its root, the curator's replies and its renewals; a raise, a wider range or a translation could be left out, and a new reader then showed the level before the raise or missed a version the alert covers. It is now listed with less than the whole thread only when the reader's code builds the same thread from what is listed.
- **A thread is renewed for 90 days after its level last changed.** Then the poster sends no more renewals and steps the level down a day before its life on readers runs out, the reply saying `This alert is N days old and is no longer renewed.`, to notice, and the alert leaves readers 90 days later. A high is on the feed for about 200 days in all. A level above the one a thread ended at raises it again and it is renewed for 90 days more; a source that still states the old level raises nothing.
- **A level nothing confirmed for 44 days is no longer raised by a reading of prose.** Such a thread was stepped down, raised again by the next candidate that read the same prose, and stepped down again a month later, for as long as candidates arrived. A candidate now raises it only when the source's fields state the level.

What an operator should know. Only the poster changes; the exporter and the CLI are as they were. The ledger gains the key `ended` on a thread that has ended, which the poster before this change refuses: once a thread has ended, 90 days after the first root posted with a claim, roll forward only. The member's CLI now applies the rest of what its own source check finds (design review of 2026-11-23, finding D8, ai-tools-alerts#tavj). Until now a relay-bot lowering applied only when the member's read of the source gave exactly that level, never below `high`, and an alert the member could not check interrupted without limit.

- **A lowering nobody can check applies after 72 hours.** When the source cannot be read, the result settles nothing or `verify = "off"`, the alert keeps its higher level, `check` says the lowering waits (`lowering_waits` in `--json`), and it applies once the signed checkpoints the CLI accepted have listed the lowering for 72 hours. The date on the lowering is not read, and a frozen mirror stops the count. A CLI the trust root calls too old, or whose ruleset is out of date, applies none unchecked.
- **A refused lowering stays refused.** When the source supports more, the lowering is not applied, as before. The refusal is now remembered, so a later reply that changes the alert's aliases or products does not turn it into an unchecked lowering; the 72 hours start only when whole reads of the sources give no more than the lowered level. The alias a refusal came through is read first among an alert's aliases.
- **Below `high`, by the claim.** A lowering to notice is confirmed when the source gives no more and every higher level the alert stated carries a signed claim, named by the alert's first id, whose fields the CLI's ruleset computes that level from. Then a withdrawn advisory confirms it, and so does a CVE that CISA no longer lists. Without such claims it takes the 72 hours. The poster does not sign claims yet (ai-tools-alerts#3qyq).
- **Critical to `high` needs no exact match.** Whole reads that give less than `high` confirm it: nothing the CLI cannot see holds more than `high`.
- **A withdrawn advisory at notice reads `confirmed`, why `withdrawn`**, not "the source does not support".
- **Two unverified interrupts per poster key per 24 hours.** A relay-bot critical the CLI has not confirmed, within the last two days, still interrupts, and its notification ends `Not verified from this machine`. A third from the same key is held: listed by `check`, named in `held_critical` of `run --json`, no notification, no exit 2, until its source confirms it or a slot is free, the alert held longest first. The slot is used when `run` reports the alert, delivered or not, and an undelivered alert is tried again on the same slot. A confirmation covers one alert a day per advisory and product: a second post about a confirmed advisory is unverified. `run` reads the source of each critical match again daily. `check` names the relay-bot matches that are not verified.
- A new state file, `unverified.json`. A damaged one is started again with one line on stderr; for 24 hours after that no unverified alert interrupts.

What it changes for a member with `verify = "off"`, or with an out-of-date CLI: every relay-bot critical is unverified, so a third within a day waits. What stays open: an alert with more than three aliases the CLI never read support through is not read whole, so its lowering takes the 72 hours; a queue of false held alerts delays a true one that cannot be verified. No wire format, schema or manifest changes; released readers keep the higher level (`tests/test_wire_compat.py`). The source check's cache is rebuilt once (version 3).

The relay bot reads GitHub's advisory database and OSV, and judges its alerts by what they state (ai-tools-alerts#3qyq, findings D4 and D13 of the design review). Until now the poster built its reading of a GitHub advisory from the vendor's HTML page, which shows no advisory type, weakness or withdrawal, so the ruleset's rows for GitHub advisories never fired and a thread that carried a GHSA id was never lowered. The poster now asks `api.github.com/advisories/<GHSA id>`, and `api.osv.dev/v1/vulns/<id>` for a `MAL-` entry a GitHub advisory names, with the same request and the same field builder as a member's own source check, so the two cannot differ on one response. A new alert takes its level from those fields: the vendor's own or a reviewed advisory with a code-execution, credential or bypass weakness and a patched version posts at high; a malware advisory at critical. An open thread is raised in the run that reads more, and lowered only under the rules of ai-tools-alerts#ny5g: every source of the thread read whole, the same lower level for 24 hours of hourly reads, seven days without a level change, and the circuit breaker. A read that fails (a timeout, a redirect, 403, 404, 429, 5xx, a body that does not parse or is cut short) is unknown: it changes no level and adds no time to a wait, and a 404 is never a withdrawal. An unreviewed advisory outside the vendor's repository lowers nothing, withdrawn or not. An id counts only when the source itself ties it to the thread's first id and it is one of the ids the member's check reads (three beside the first), so the bot publishes no level that check cannot confirm. Advisories grouped by one fixed release now post under the member whose own evidence supports the highest level, not always the newest, so the group's level is one its first id supports. A thread whose CVE the KEV catalog lists is marked exploited in the ledger in that run, whether or not its level changes, and is then lowered on a later absence only under the KEV rules of ai-tools-alerts#ny5g. An alert posted at critical with "stop using" falls to high once its advisory states a patched version the thread cannot offer. A withdrawn advisory lowers its thread to notice or to what its prose supports and no further: the reversible `withdrawn` state is ai-tools-alerts#y484, and the claim on each event is ai-tools-alerts#hh5s.

When a share runs out the poster says how many ids it did not read on stderr; those threads do not move that run. With more than ten advisory ids waiting, or more than ten others, waits stop growing and nothing is lowered on advisory evidence; raises still publish, late by at most as many hours as there are threads. The CLI now reads the primary source of an alert itself and says whether the source supports it (design review of 2026-11-23, findings D7 and D8, ai-tools-alerts#fv4g). `aitools-alerts run`, which the hourly job runs, and the new `aitools-alerts verify` read three addresses fixed in the code: the CISA KEV file, `api.github.com/advisories/<GHSA id>` and `api.osv.dev/v1/vulns/<id>`. Each product of each relay-bot alert is `confirmed`, `contradicted` or `unknown`. Only a response with status 200 that arrived whole and parsed completely can confirm or contradict; a timeout, a redirect, 403, 404, 429, a server error or a body cut short is `unknown`. A known-exploited CVE attached to the wrong product is `contradicted`, and one product the source supports never confirms another in the same alert. A source its subject's attacker can write (an advisory GitHub has not reviewed) confirms nothing and contradicts nothing, and neither does CISA not listing a CVE. The check covers the product and the level, not the version range a post states. `check` and `plan` print a `source check:` line for each contradicted product; `check --json` and `run --json` gain `source_check` on each match. Results are kept in `verify.json` in the state directory, bound to the ruleset's digest, with no text from a source except an ETag and the ids it names.

**This release reports the result and changes nothing else:** levels, matches, notifications and auto-apply are as posted. Applying the result (accepting a relay-bot lowering the source confirms, keeping the higher level when it does not) is ai-tools-alerts#tavj. The new config key `verify = "matched" | "all" | "off"` (default `matched`) chooses which alerts are read; the README says what each value tells GitHub and OSV about your machine. A member's machine now makes up to 10 requests an hour to those three hosts; `verify = "off"` stops them.

An alert's level is now a function of structured source fields that a member's CLI can compute, and a model's reading no longer makes a critical (design review of 2026-11-23, findings D2, D3, D10 and D11, ai-tools-alerts#s6mt). Before, two of the three critical rules rested on flags a model set from advisory prose. The relay bot now posts those as `high`; critical comes only from a field: CISA KEV lists the CVE for that product, a GitHub malware advisory names its package, or the vendor's own repository advisory states embedded malicious code (CWE-506). Every other level the bot computes is unchanged, and a thread already posted is never lowered by this.

`spec/ruleset.json` holds the level table, the days each level stands, and the table of which source may set which level: an OSV `MAL-` entry alone is `high`; an advisory nobody reviewed, or one from a repository that is not the product's own, is a `notice` whatever it says, and its withdrawal justifies no lowering. A source binds to a product only by the exact identities of `spec/scope.json`, so a KEV entry for another vendor's product supports nothing here. `aitools_alerts/ruleset.py` evaluates it for the poster and the CLI and imports nothing from the poster.

The claim a poster will sign with each alert is defined: `{id, source, fields, ruleset, level, confirmed_at, checked_at}`, carrying the fields themselves, with one canonical byte form (every string printable ASCII, so no Unicode version decides what a name binds to) and test vectors in `spec/claim-vectors.json` that both test suites load. `ruleset.check_claim` is the offline check: the reader computes with its own ruleset, never the one a claim names, so a claim citing an older rule under which the level was lower does not pass; given the root's pin it refuses a claim below `min_version` and judges nothing when its own ruleset is older than the pin allows. The ruleset and the scope file have one SHA-256 digest (`ruleset.load().digest`).

Not in this change: nothing new is on the wire or in the state file, the CLI does not yet check anything against a source, and the trust root does not yet pin the ruleset (ai-tools-alerts#ed7n, the first entry above: the pin is a key of the checkpoint key certificate, beside `min_cli`, because every released reader refuses a manifest with a key it does not know). The poster reads the vendor's advisory page, which shows no CVSS vector, weakness list or review state: those fields are empty in its claims until it reads the advisory API.

The wire format of the self-correcting design is fixed before anything uses it (design review of 2026-11-23, finding D12, ai-tools-alerts#t8jr). The v2 design said that 0.1.x readers ignore fields they do not know. They do not: a new key in an alert's block makes every released CLI drop the alert, with no error; a new key in the manifest makes every released CLI refuse the pull; a relay-bot reply that lowers a level is skipped (whole before 0.1.7; 0.1.7 still joins its products, actions and sources). `spec/wire.md` now states where new signed data may go, and `tests/test_wire_compat.py` runs the released readers (0.1.4, 0.1.5, 0.1.6, 0.1.7, each unpacked from its tag) against a feed in the new format: every alert is still shown, at the same level or a higher one, to the member whose machine it matches.

- The alert block and the manifest do not change. A test holds `spec/advisory.schema.json` to the 0.1.4 file, byte for byte.
- The claim (what an alert's level rests on) will travel in one event tag, `["claim", "<JSON>"]`, which every released reader ignores. `aitools_alerts/wire.py` reads and writes the tag; what goes in it comes with ai-tools-alerts#s6mt.
- A lowering by the relay bot will be a reply that carries the new level and nothing else, and so will every later level change on that thread. **Readers at 0.1.7 and earlier refuse a relay-bot lowering and keep the higher level.** That is the safe direction, and it is permanent for those releases: after the bot lowers an alert, an old CLI goes on showing it at the level it had. Because the lowering travels alone, a fix or a source posted around it still arrives. The poster's composer now refuses to put a lowering in a reply with anything else.
- A relay-bot post sets no expiry: `expires_at` stays null in an alert and is never in a reply (the composer refuses it). Every released reader stops showing an alert at that time and takes no renewal from the bot, so an expiry in the block would end true alerts on old CLIs. The design's expiry will be computed from the claim.
- The trust root can name the oldest release that reads the feed in full: `min_cli`, an optional key of the checkpoint key certificate (`scripts/sign-checkpoint-key.py --min-cli N.N.N`). A CLI older than it prints one `upgrade:` line after every command that reads the feed and keeps working; `run --json` gains the key `min_cli`. It is in the certificate and not in the manifest, where the design had put it, because of the second fact above. No certificate carries it yet. The 0.1.7 release and earlier ignore the key and never print the line; it speaks to the next release and later ones.

Expiry is computed by the reader and judged by the signed checkpoint, not by the member's clock (design review of 2026-11-23, finding D5, ai-tools-alerts#r0ra). Before, an alert with `expires_at` ended when the machine's clock passed it: a frozen mirror ended it with no key, a clock set ahead ended it at once, and the relay-bot key could post an alert that expired one second later. Now:

- A relay-bot alert's `expires_at` is not read. Only a curator's ends a thread.
- An alert whose first post carries a claim stands for the days `spec/ruleset.json` gives its level after the claim's `confirmed_at` (critical 14, high 30, notice 90). A later claim on the thread renews it. A check that could not confirm holds the level up to 45 days from the last confirmation. When a level's days run out the alert shows at the next level down that still stands (a critical is high until day 30 and notice until day 90), and then it is gone. The longest claim counts; a short one shortens nothing, and a reply that sets a level counts from its own date.
- The clock for all of this is the issue time of the newest checkpoint the CLI holds, and an alert decays only under a checkpoint that lists it. A frozen mirror, a mirror that withholds a renewal (already refused as `mirror incomplete`) and a wrong clock expire nothing; the stale warning says why.
- A pull no longer ages stored alerts out by the machine's clock when it holds a checkpoint: a clock a year ahead used to delete every stored alert older than 35 days.
- A relay-bot alert whose first post has no claim does not expire. That is every relay-bot alert on the feed today: the poster sends no claim yet (ai-tools-alerts#gtw9). A curator's alert with `expires_at` still ends, now by the checkpoint's time: it stays while the CLI holds no checkpoint past that time that lists it.

Not done: the issue asked that an event dated after the checkpoint that lists it be refused. The poster's own checkpoint lists the posts of its run, which are dated after it, so the CLI does not judge an alert's expiry while one of its claims is dated after the checkpoint; the next checkpoint judges it.

The poster sends no claim yet (ai-tools-alerts#3qyq). The one new event it sends is the level-only lowering described above. The relay was checked before this release: it stores and returns a 2048-byte claim tag, and the mirror exporter copies it, byte for byte (ai-tools-alerts#yw7r).

## 0.1.7 — 2026-11-24

The relay bot posts an alert once, when it is complete, and only while it is news (ai-tools-alerts#0dvh, rebuilt on the authoritative-source rule by ai-tools-alerts#dmmf). A high whose vendor page states neither a fixed version nor an affected range waits up to six hours from first sight for one, and then posts with what is known; a critical and a known-exploited entry never wait. An advisory whose primary source was published more than seven days before the poster first saw it goes to the digest's Notice section, never to a real-time root, unless CISA has just listed it as exploited. The block carries the severity word the vendor's page states (never a collector's), a reply carries a changed severity only when it changes something else too, and a range the schema cannot express makes the post say "affected versions: see the source" instead of "versions not stated". Titles and headlines name the public id (`CVE-2026-103435`), while the block id stays the thread key, so installed readers keep matching threads. The mirror page lists a critical once, not once per channel. The state file gains a `waiting` key. A rollback removes the hold and the age limit only and keeps the new titles and severity handling, which threads already posted need.

A reply from the relay bot can no longer take an alert away from members (design review of 2026-11-23, finding D1, ai-tools-alerts#tyje). The CLI already refused a bot reply that lowered an alert's level or set an expiry. It still applied one that lowered `fixed` to `0.0.1`, replaced `products` with a product nobody runs, emptied `actions` or replaced `sources`: the first two remove the alert from every member's `check` while the thread still reads critical, so whoever held the bot's key could silence any bot alert with one signature. Now the `products`, `actions` and `sources` of a reply from a key that is not a curator's are joined to the thread's, never put in their place. The reply may add a product, widen `affected`, raise or clear `fixed`, add an action, raise an upgrade's version, add a source. A product it leaves out stays; a narrower `affected`, a lower `fixed`, a `fixed` where there was none, a weaker action or a missing source changes nothing; the rest of the reply applies. The result is the same in whatever order a thread's replies are read, so a reply dated before an earlier one cannot undo it. The same rule governs the mirror page and the Atom feeds, which are built by the same code. A curator's reply is unchanged: it replaces fields whole.

What the bot's key can still do to its own alert: add entries, add a source (a new source on a primary domain is shown before an older one that is not), and clear `fixed`, after which the member is told to upgrade with no version and only a curator can name one again. Consequences of the rule: a true narrowing from the bot is left out like a forged one: when a vendor publishes a fix for an alert that had no fixed version, members at or above that version keep seeing the alert until a curator signs the change (the member's own check against the source, ai-tools-alerts#h29n, will lift this). A bot reply that changes an entry into one neither wider nor narrower adds it beside the first, so a thread can list a product twice and a member can match both; `curator amend --fixed NAME=VERSION` now sets every entry of that product, and `curator amend` works on a thread whose lists the bot has grown past the schema's limits. Nothing tells a member or a curator yet that a narrowing was left out (ai-tools-alerts#2wa6). And readers at 0.1.6 and earlier still apply a narrowing reply whole; they are protected only once they install 0.1.7 or later. No wire format changes: the advisory block, the events and the poster are as before.

## 0.1.6 — 2026-11-24

The feed checkpoint is in force. `trust/checkpoint-key.json` is the root-signed certificate for the poster's checkpoint key (signed 2026-11-23, expires 2027-03-23), and readers of this release refuse a pull until they hold a valid certificate (this one is bundled, and the mirror serves it) and the mirror serves a checkpoint signed by the key it names.

The CLI accepts an event only when it is a kind 9 message with one `h` tag naming an alert channel in `spec/channels.json`. Before, anything a poster's key had ever signed, anywhere, could be served by the mirror as an alert, a patch or a retraction (security review of 2026-11-23, finding M3). It also refuses a new event dated more than 10 minutes ahead of the local clock: one event dated years ahead used to count as fresh news for years and silenced the warning about a frozen mirror (finding H2). Events already stored are kept whatever their date, so a clock that jumps back cannot undo a stored retraction; they only stop counting as fresh news. The pull summary counts both as `not-channel-post` and `future-dated`. The mirror exporter publishes neither kind of event, which protects installed v0.1.4 readers from the future-dated one.

The CLI now checks that the feed is complete, not only that each post is signed (security review of 2026-11-23, finding H2). Every pull also fetches a certificate from the trust root naming the checkpoint key, and a checkpoint from that key listing the posts that exist. A new post is admitted only when a checkpoint lists it; a mirror that lacks a listed post is refused (`mirror incomplete`); an older checkpoint or certificate is refused; a post the CLI has applied stays applied, so no checkpoint can take a retraction away. The manifest and the certificate are also fetched from a second origin (this repository; `second_origin` in `config.toml`), and the higher manifest wins. `stale_since` now means no fresh checkpoint, in place of the 3-day and 90-day rules. A new state `unverified` (in `check`, `plan` and `run --json`) says why the CLI cannot vouch for completeness: the last pull failed, no fresh checkpoint, an expired certificate. While it holds, `plan` lists nothing under auto-apply. The session-start hook's second line now reads "stale or unverified"; a hook copied from an earlier release still fires, because `stale_since` is non-null in every unverified state. This CLI must not be released before the mirror serves the two new files: until then every pull ends `no checkpoint key certificate`.

The fleet side of the checkpoint: the poster signs one at the end of every run with a key that stays on its own machine (`checkpoint_key_file`, `aitools-alerts-poster checkpoint-keygen`), listing the posts on the mirror and every post the relay acknowledged until the mirror shows it; the relay VM gains one guarded command that only stores it (`ops/vm/mirror-put`); the mirror exporter publishes the certificate and the checkpoint only after verifying them, and the checkpoint only together with every post it lists (`--checkpoint-key`, `--inbox`). None of it is active until the poster's config and the VM are set up (`ops/vm/README.md`).

Two signed documents are defined for that (`aitools_alerts/checkpoint.py`): a certificate, signed by the trust root, naming the one key that may sign feed checkpoints, and the checkpoint itself, which lists the events that exist so that a mirror cannot leave one out unnoticed (security review of 2026-11-23, finding H2). `scripts/sign-checkpoint-key.py` signs the certificate. Installed readers (0.1.5 and earlier) never fetch them.

The relay bot signs only what an authoritative source states (security finding H4 of the 2026-11-23 review, ai-tools-alerts#h340). Before this, anyone could publish an advisory for a package of their own named `claude-code-router`, and the bot would post "upgrade Claude Code to 99.0.0 or later": the product was matched by words in free text, a high needed no source, and the version, title and ids came from the upstream record. Now a product is matched only by exact identity (`spec/scope.json` version 5: names, repository slugs, package keys such as `npm:@anthropic-ai/claude-code`, and CISA KEV vendor and product pairs); a candidate posts at any level only when the CISA KEV catalog or a page of the product's own vendor confirms it; and the ids, fixed version, affected range, title and severity word of a post are read by the poster from that page. Posts name CVE and GHSA ids only and list only the page that confirmed them. An advisory a vendor publishes on its own site only, with no repository advisory, posts as a digest notice. Fewer advisories post: one whose only source is the global GitHub advisory database, NVD, a distribution tracker or news does not. The advisory block is unchanged, so every released reader parses the new posts. Poster-side only; no change to the member CLI. On its first run the new poster discards unsent posts, held notices and deferred candidates composed under the old rules, and says so on stderr.

The poster signs every post on the poster machine and sends it to the relay over HTTPS (`POST /events` with a NIP-98 header); it no longer sends through an ssh wrapper on the relay VM, and the relay VM keeps no key that may post. Before this, whoever took the relay VM could read the bot's key and sign alerts members' CLIs accept (adversarial review finding H1, ai-tools-alerts#vzc3). The poster config drops `relay_send_wrapper` and takes `relay_key_secret` (and `relay_url`, defaulting to the relay); `secrets_helper` is now required to run. `relay_ssh_host` now names only the feed checkpoint's put-only route, and goes with `checkpoint_key_file` and `relay_put_wrapper`; the guard on the VM allows `mirror-put checkpoint` alone. `ops/vm/scan-for-poster-keys.py` checks a machine for any poster key, in files and nested archives, by public key.
