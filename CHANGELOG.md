# Changelog

## 0.2.0 — 2026-11-25

The poster settles an unknown or refused send by itself (ai-tools-alerts#jsje; ruling of 2026-11-23, no human in the loop). Until now a send whose outcome was unknown held every later change to its thread, a raise included, until someone ran `aitools-alerts-poster resolve`, and a send the relay refused waited in `withheld` the same way. Now each run settles them first. An unknown send is delivered when the mirror shows an event signed by the relay-bot key with the same text, channel and thread, dated from the attempt on; the run records it as `resolve --delivered` does. One that a mirror generated within the last hour does not show 24 hours after the attempt is sent again, and so is one that no mirror has shown after 72 hours. A refused send is dropped three days after the refusal and its advisory composed again; a refused reply that another channel already has is sent once more as it is, and dropped only when refused again. The next digest adds the dropped posts to its "withheld by the publication check" count, on a quiet day too. A raise no longer waits behind lower-priority work on its own thread: an unsent level reply below the raise, and an unsent reply that only lists ids and sources and that no channel has, are removed and the raise goes out. It still waits while a send of that thread is unknown, and behind a reply that carries a fix. A lowering whose send was unknown and has expired is sent again, never dropped, since a channel may have it. `pending` and `resolve` still work.

What an operator should know. The poster can now post twice with no one deciding it: when a send did post but the mirror, claiming to be fresh, did not show it within 24 hours, or did not show it at all within 72. The summary line gains `settled=delivered:N,resent:N,dropped:N,superseded:N` in a run that settled something, and each case is one line on stderr. The poster state gains `dropped` (posts dropped since the last digest), a digest item's snapshot may carry `dropped`, and a journal item may carry `tried` (its first attempt with an unknown outcome). To roll back, stop the poster's timer, then rewrite the state file in place, since the previous version refuses these keys: `jq 'del(.dropped) | (.outbox[], .withheld[].items[]) |= (del(.tried) | if .kind == "digest" then del(.adv.dropped) else . end)' state.json > state.json.new && mv state.json.new state.json` (the state file is the config's `state`, beside the ledger by default), and start the timer again.

The daily digest is short, and the notices move to a weekly summary (ai-tools-alerts#qwpw, design section 7 of ai-tools-alerts#9mx8). The daily digest at 09:00 Tokyo lists each alert the relay bot posted since the last digest, one line each with its level (`- HIGH: <title>; fixed in <version>. <source>`), and nothing else: no level sections, no notices, no grouping of one vendor release's CVEs (one post per fix already does that). A thread is listed once, by its root; a fix or level change later is a reply in its thread and is not listed again. A day with no new alert posts one line: `no new alerts. N notices added to the catalog this week: https://buzz.ai-tools.md/alerts/`. The first digest of each week, Monday's (or the next one when Monday's run was missed), adds a weekly summary: the week's notices counted by product, counts only, with the link. A notice is summarized once. One that has since posted an alert, or was retracted or expired, is dropped from the count. The CLI does not read the digest: its freshness signal is the signed checkpoint. The poster state gains `weekly`, the ISO week of the last summary; a state from before starts at the current week, so the first summary is the next Monday's. To roll back, also run `jq 'del(.weekly) | (.outbox[], .withheld[].items[]) |= (if .kind == "digest" then del(.adv.week) else . end)'` on the poster state, which the previous version refuses otherwise.

Advisories for one product that one release fixes are now one post (ai-tools-alerts#faxq, design sections 5 and 6 of ai-tools-alerts#9mx8). When one run sees several advisories for the same product, none of them with a thread yet, and they state the same fixed version, the relay bot posts one root: its block names every id (`id` and `aliases`), its level is the loudest member's, and its range covers every member's (theirs when they agree, none stated when one states none, else everything before the fix). The five `mcp-server-git` posts of 2026-11-18 would have been one. A later advisory with the same fix still posts its own root (ai-tools-alerts#btqg). A run no longer replaces a thread's stated fix with an older one.

The post reads differently. A root is five lines: the headline (the level and the source's own title, at most 90 characters, no id), `Affected:` (the package as a member installs it, the range, the registry), `Do:` (one sentence: upgrade to the fixed version; with no fix, apply the source's workaround until a fixed release ships; never "check the vendor"), `Covers N advisories:` with each id, and `Source:`. The Japanese copy has the same lines. The `aitools-alert` block is one line of compact JSON; its keys and values are unchanged, and every released reader parses it (`tests/test_wire_compat.py`). The block's `title` keeps its form with the id. Replies use the same words and drop the `Now:` title line.

A model can write a high or critical alert's first line and a `Who:` line after it, naming who is exposed (ai-tools-alerts#c6ak, design section 6 of ai-tools-alerts#9mx8). It is off by default: `model_wording = true` in the poster's config turns it on, and it needs `secrets_helper`. It uses translation's key, model, call path and hold, reads the vendor's advisory text or the KEV entry's description, and makes at most 4 calls a run. A fixed check in `aitools_alerts/poster/wording.py` refuses a draft that is too long, holds a URL, a command, an advisory id, an `@`-name, or a word or capitalised name the advisory does not write; a refused draft, a model error or a missing key posts the source's own title and no `Who:` line, as before. Both lines are prose: the block the CLI reads is the same with or without them, and the Japanese reply takes the headline but not the `Who:` line. With it on, the summary line ends `wording=<worded>/<asked>` (or `held`, `key-error`, `error`). Before reinstalling an older poster, remove `model_wording` from the config.

A curator's word on one of the relay bot's alerts is now checked and held for 14 days, and it no longer silences the bot (design review of 2026-11-23, finding D9, ai-tools-alerts#c1g2). Until now one curator signature lowered or retracted any alert for good with no check, and every later reply from the bot to that thread was ignored, so the thread could never be raised or corrected again. The one curator in the manifest is a shared key, and no curator has posted.

- A curator's lowering, narrowing, expiry or retraction of a relay-bot alert holds for 14 days from its date, by the signed checkpoint's time. Then the alert is back as its signed replies give it, unless the curator signed the action again (`aitools-alerts curator renew <id>`, new) or the member's own source check confirms the lowering.
- When the member's source check finds that the source supports more than a lowering or a retraction says, it is not applied on that machine at all, and `check` says so: `source check: a lowering of <id> to <level> is not applied: the source supports <level> for <product>`. `run` shows and notifies such a critical in the run that reads the source. `check --json` and `run --json` carry `lowering_refused` on each match.
- During a curator's 14 days a relay-bot raise shows at once. The bot's other changes show when the hold ends.
- A relay-bot lowering is no longer only refused. A reply that carries nothing but a lower level is kept as the alert's published level, and a member's CLI applies it when its own read of the source, no more than two days old, gives exactly that level. In this release that is a lowering from critical to high: nothing is lowered below `high` this way, because a `high` may rest on a reading of the source's text. With `verify = "off"`, or when the source cannot be read, the higher level stays. This is the first part of ai-tools-alerts#tavj; the 72-hour rule for members who cannot read a source is not built.
- An alert a curator posted is unchanged: a curator's word on its own alert stands, the bot's replies to it are discussion, and only such an alert is ever auto-applied.
- `curator amend` and `curator retract` work on an alert as it stands now, after any lapse, and say when the hold ends.

What stays open: a curator key can renew a hold every 14 days where a member's source cannot settle the question, and can narrow an alert's products unchecked for 14 days. The next manifest names no curator, and the role then moves to a key used for nothing else (ai-tools-alerts#r98k). A released CLI (0.1.8 and earlier) still takes a curator's word as final. No wire format, schema, manifest or state file changes.

The trust root can pin the ruleset, and a CLI whose ruleset is out of date says so and stops judging (design review of 2026-11-23, finding D10, ai-tools-alerts#ed7n; the second half of ai-tools-alerts#s6mt). The pin is `ruleset: {version, sha256, min_version}`, an optional key of the checkpoint key certificate beside `min_cli`, signed with `scripts/sign-checkpoint-key.py --ruleset-min-version N`: the version and digest are those of the checkout the root signs from. A CLI is out of date when its ruleset is below `min_version`, or is the pinned version with another digest (`ruleset.outdated`, which `ruleset.check_claim` now shares). It then prints one `out of date:` line after every command that reads the feed, and `run --json` gains the key `ruleset_outdated`.

**An out-of-date CLI hides nothing and lowers nothing.** It shows and notifies every alert as posted. It reads no primary source, prints no source check result (a cached one included), gives `source_check: null` in JSON, and applies no computed expiry: a relay-bot alert keeps the level its posts give instead of ageing down by a TTL table the root has replaced. So an alert can show longer, or at a higher level, than on a current CLI, and `run` exits 2 for an unseen critical that a current CLI would by then show lower.

A pin the CLI cannot read (a later form of it) does not refuse the certificate. The CLI takes it as a pin it does not meet: out of date, with `ruleset_outdated` giving `pinned: null`. Refusing the certificate would have left the CLI on the older certificate it holds, with no pin at all. The signing script still refuses to sign a malformed pin.

**No certificate carries the pin yet, and nothing changes until one does.** The 0.1.6, 0.1.7 and 0.1.8 releases ignore the key and pull as before (`tests/test_wire_compat.py` runs the three against a certificate that pins a ruleset none of them has); 0.1.4 and 0.1.5 never read the certificate. The issue first put the pin in the manifest: every released reader refuses a manifest with a key it does not know and fails the pull, which is why it is in the certificate. The pin lasts as long as its certificate: pass `--ruleset-min-version` again on each later one, or the script warns that the pin is dropped.

The poster can now post every in-scope advisory to a catalog channel, and the mirror can serve it as `catalog.json` (ai-tools-alerts#q03f, design section 1 of ai-tools-alerts#9mx8). The switch is `spec/catalog-channel.json`, which names the channel; this release carries it, naming `#security-catalog` (`91df2256-31b6-4ebf-b60a-b45a221f5978`, ai-tools-alerts#q3fd). Without the file nothing changes. The channel posts are unchanged. Released readers never fetch `catalog.json`, and no catalog event is ever in `feed.json`, `critical.json` or the checkpoint. Reading and matching the catalog in the CLI is ai-tools-alerts#8nb4. `docs/design.md`, "Catalog channel", has the rules.

What an operator should know. With the file present the poster writes three more files beside the ledger, `<ledger>.catalog-known.json`, `<ledger>.catalog.json` and `<ledger>.catalog.lock`, and its summary line ends `catalog=<sent>/<waiting>`. Losing the first two only makes the lane post again, which is harmless. The catalog's sends come after the ledger lock and the checkpoint and never change the exit code. The poster reads the copy of `spec/catalog-channel.json` inside its installed package, so it follows the release installed, not a checkout. The exporter reads it from its own deployed copy (or `--catalog`), and a catalog failure leaves the alert files as they would have been. To go back: install a release without the file, or delete the file from the installed package and from the exporter's copy.

The CLI now matches an MCP server by the package it runs, not only by the key it is configured under (ai-tools-alerts#0xq6, design section 8 of ai-tools-alerts#9mx8). For each server in the Claude Code, Codex and Cursor configs it reads `command` and `args` and works out the package: `npx`/`bunx` with an npm name, `uvx`, `uv tool run` and `pipx run` with a PyPI name, a path into `node_modules` (the version from that package's `package.json`), or a path into a virtual environment's `bin` (the version from its `.dist-info`). A pinned version (`@1.2.3`, `==1.2.3`) is kept; a tag or a range is not a version. Only the package name and the version enter the inventory, each in a fixed grammar; no argument, environment value or URL does, and nothing is run. An alert names the package (`spec/scope.json`), and the scope entry's `package` says which registry the name belongs to, so an npm package that happens to share a PyPI server's name does not match it. Nothing on the wire changes.

Hermes and OpenClaw are probed. Hermes's version comes from the `pyproject.toml` of its default install (`~/.hermes/hermes-agent`); `hermes --version` is not run, because it checks for updates over the network. OpenClaw's comes from `openclaw --version`. A Claude Code plugin is listed with its marketplace (`name@marketplace`); an alert naming `name@marketplace` matches only that plugin from that marketplace.

A match by a name alone, or one with no installed version to compare to a stated range, is now reported with reason `may apply` (it was `name`). It is printed and is in `--json`, but it never sets exit 2, never sends a notification and is never auto-applied. A product that says every version is affected (`*`, no fix) still matches as `affected` when the package or the plugin's marketplace confirms the installation. Because a product with no range no longer interrupts, a relay-bot reply that drops a product's range no longer replaces the bounded product: the thread keeps both, and the bounded one still interrupts. The session-start skills and the AGENTS.md snippet tell a person a `may apply` match last, as a possibility.

## 0.1.8 — 2026-11-24

A level is now set by its consequence to the member, and a critical needs an action the member can take (ai-tools-alerts#9kgk, design section 4 of ai-tools-alerts#9mx8). Ruleset version 3: a critical stands only when the post carries a complete action, an upgrade while the post states the fixed version, or `stop_using` for a malicious release a reading confirms (GitHub malware, a vendor's CWE-506); otherwise it is `high`. A KEV listing with no fix known therefore posts at `high`. The upstream severity word is printed and never sets a level. A channel product's `high` needs code execution, credential or token theft, or a sandbox or approval bypass, with a fix; everything else is a notice, denial of service included. The poster, the curator command and the member's source check (`verify`) apply the same rule (`Ruleset.action_level`). A known thread is raised to critical only when its root stated the fix, because every reader holds a fix that a later reply adds (ai-tools-alerts#tyje); such a thread stays `high` with its fix until a source check can confirm the held fix. The synthetic check (`run --kev-file`) now posts at `high` (ai-tools-alerts#a3xh).

What an operator should know. The ledger keeps the fix a thread's root stated (`root_fixed`). An older poster refuses a ledger with that key: to go back, remove `root_fixed` from every ledger entry, as well as the keys the entry below names.

The relay bot now lowers a level itself, and only on evidence it has held for a day (design review of 2026-11-23, findings D4, D13 and D15, ai-tools-alerts#ny5g). Every run it recomputes the level of each thread that rests on the CISA KEV catalog. A raise is posted in the run that sees it. A lowering needs all of this: the catalog read whole (it came from CISA's address with no redirect, it has a version, it agrees with its own count, and it has at least 98% of the entries of the largest whole copy the poster has ever read); the same lower level for 24 hours, counted only from one whole read to the next when they are at most two hours apart and no failed read lies between, so an outage adds no time; a later catalog version at the end than at the start, and never an older catalog than the latest one read; for every CVE of the thread that is gone, a whole copy that listed it before; and seven days without a level change on that thread, which gives at most three level changes a week and never holds a raise back. A fetch that fails (a timeout, a 404, a 429, a 5xx, an empty or cut body) changes no level and starts no wait. When more than two threads and more than a fifth of those that rest on the catalog are due at once, none is lowered and the digest says so; after seven days of that, two a run go through. The bot has no retraction: `notice` is the lowest it goes.

A level that a reading of prose supports is never lowered by this. The ledger now keeps that level per thread (`floor`); a thread posted before this change is lowered to `high` at the lowest. The one critical the service has sent, the OpenSSH thread CVE-2026-123158, is therefore lowered to `high` a day after the first run of this change, with no curator: OpenSSH is outside the channel class since scope version 6, where a KEV entry supports a notice. A thread that carries a GitHub or OSV advisory id is not lowered yet, because the poster cannot read those sources as fields (ai-tools-alerts#3qyq, which also brings the reversible `withdrawn` state and the claim tag).

**No released reader applies a lowering from the bot, and neither does this one yet.** A lowering is a reply that carries the new level and nothing else, in each channel the thread has a post; every CLI up to this change refuses it and keeps the higher level, which is the safe side. The CLI's own check against the source (ai-tools-alerts#fv4g, below) reports what the source supports; accepting a lowering on that check is ai-tools-alerts#tavj. Until then a lowering shows in the digest, which lists the ids lowered since the last one in one line, and in the level the digest files the thread under. On a thread that has been lowered, every later level change travels alone too, and a fix learned in the same run follows in a second reply (`spec/wire.md`, rule 2).

What an operator should know. The poster writes one more file beside the ledger, `<ledger>.recompute.json`; if it is lost, every wait starts over and no absence counts until the catalog has listed the CVE again. If CISA ever removes more than 2% of the catalog, the poster stops lowering on KEV absences and says so on stderr each run; raises are unaffected. A send whose outcome is unknown still holds every change to its thread until `resolve` settles it, a raise included (ai-tools-alerts#jsje). To go back before any thread is marked lowered: remove `lowered`, `changed` and `floor` from every ledger entry and `floor` from every journal item, and delete the recompute file. Rollback is one-way once a thread is marked lowered: an older poster refuses a ledger with the new keys, and that refusal is intended, because it would not send a later raise alone. To go back: stop the poster; in every entry marked `lowered` set `level` and `advisory.level` to the highest level the thread has had; in the state file remove every `outbox` item and `withheld` group whose key holds `#level:`, set `adv.level` to that same level in every other item of such a thread, and remove the `floor` key from every item; remove `lowered`, `changed` and `floor` from every ledger entry; delete the recompute file.
The CLI now reads the primary source of an alert itself and says whether the source supports it (design review of 2026-11-23, findings D7 and D8, ai-tools-alerts#fv4g). `aitools-alerts run`, which the hourly job runs, and the new `aitools-alerts verify` read three addresses fixed in the code: the CISA KEV file, `api.github.com/advisories/<GHSA id>` and `api.osv.dev/v1/vulns/<id>`. The id comes from the alert's id and aliases and must have the exact form of a CVE, GHSA or `MAL-` id; no link from a post is ever opened, and which other ids are the same advisory is taken from the source, never from the post. Each request is https, follows no redirect, and is bounded as a whole to 10 seconds and to 8 MB (KEV) or 256 KB; a run makes at most 10 requests in 30 seconds. `run --json`, which the session-start hook runs, reads no source.

Each product of each relay-bot alert is `confirmed`, `contradicted` or `unknown`. Only a response with status 200 that arrived whole and parsed completely can confirm or contradict; a timeout, a redirect, 403, 404, 429, a server error or a body cut short is `unknown`. A known-exploited CVE attached to the wrong product is `contradicted`, and one product the source supports never confirms another in the same alert. A source its subject's attacker can write (an advisory GitHub has not reviewed) confirms nothing and contradicts nothing, and neither does CISA not listing a CVE. The check covers the product and the level, not the version range a post states. `check` and `plan` print a `source check:` line for each contradicted product; `check --json` and `run --json` gain `source_check` on each match. Results are kept in `verify.json` in the state directory, bound to the ruleset's digest, with no text from a source except an ETag and the ids it names.

**This release reports the result and changes nothing else:** levels, matches, notifications and auto-apply are as posted. Applying the result (accepting a relay-bot lowering the source confirms, keeping the higher level when it does not) is ai-tools-alerts#tavj. The new config key `verify = "matched" | "all" | "off"` (default `matched`) chooses which alerts are read; the README says what each value tells GitHub and OSV about your machine. A member's machine now makes up to 10 requests an hour to those three hosts; `verify = "off"` stops them.

An alert's level is now a function of structured source fields that a member's CLI can compute, and a model's reading no longer makes a critical (design review of 2026-11-23, findings D2, D3, D10 and D11, ai-tools-alerts#s6mt). Before, two of the three critical rules rested on flags a model set from advisory prose. The relay bot now posts those as `high`; critical comes only from a field: CISA KEV lists the CVE for that product, a GitHub malware advisory names its package, or the vendor's own repository advisory states embedded malicious code (CWE-506). Every other level the bot computes is unchanged, and a thread already posted is never lowered by this.

`spec/ruleset.json` holds the level table, the days each level stands, and the table of which source may set which level: an OSV `MAL-` entry alone is `high`; an advisory nobody reviewed, or one from a repository that is not the product's own, is a `notice` whatever it says, and its withdrawal justifies no lowering. No two sources add up to a level neither gives alone. A source binds to a product only by the exact identities of `spec/scope.json`, so a KEV entry for another vendor's product supports nothing here. `aitools_alerts/ruleset.py` evaluates it for the poster and the CLI and imports nothing from the poster.

The claim a poster will sign with each alert is defined: `{id, source, fields, ruleset, level, confirmed_at, checked_at}`, carrying the fields themselves, with one canonical byte form (every string printable ASCII, so no Unicode version decides what a name binds to) and test vectors in `spec/claim-vectors.json` that both test suites load. `ruleset.check_claim` is the offline check: the reader computes with its own ruleset, never the one a claim names, so a claim citing an older rule under which the level was lower does not pass; given the root's pin it refuses a claim below `min_version` and judges nothing when its own ruleset is older than the pin allows. The ruleset and the scope file have one SHA-256 digest (`ruleset.load().digest`).

Not in this change: nothing new is on the wire or in the state file, the CLI does not yet check anything against a source, and the trust root does not yet pin the ruleset (ai-tools-alerts#ed7n, the first entry above: the pin is a key of the checkpoint key certificate, beside `min_cli`, because every released reader refuses a manifest with a key it does not know). The poster reads the vendor's advisory page, which shows no CVSS vector, weakness list or review state: those fields are empty in its claims until it reads the advisory API.

The wire format of the self-correcting design is fixed before anything uses it (design review of 2026-11-23, finding D12, ai-tools-alerts#t8jr). The v2 design said that 0.1.x readers ignore fields they do not know. They do not: a new key in an alert's block makes every released CLI drop the alert, with no error; a new key in the manifest makes every released CLI refuse the pull; a relay-bot reply that lowers a level is skipped (whole before 0.1.7; 0.1.7 still joins its products, actions and sources). `spec/wire.md` now states where new signed data may go, and `tests/test_wire_compat.py` runs the released readers (0.1.4, 0.1.5, 0.1.6, 0.1.7, each unpacked from its tag) against a feed in the new format: every alert is still shown, at the same level or a higher one, to the member whose machine it matches.

- The alert block and the manifest do not change. A test holds `spec/advisory.schema.json` to the 0.1.4 file, byte for byte.
- The claim (what an alert's level rests on) will travel in one event tag, `["claim", "<JSON>"]`, which every released reader ignores. `aitools_alerts/wire.py` reads and writes the tag; what goes in it comes with ai-tools-alerts#s6mt.
- A lowering by the relay bot will be a reply that carries the new level and nothing else, and so will every later level change on that thread. **Readers at 0.1.7 and earlier refuse a relay-bot lowering and keep the higher level.** That is the safe direction, and it is permanent for those releases: after the bot lowers an alert, an old CLI goes on showing it at the level it had. Because the lowering travels alone, a fix or a source posted around it still arrives. The poster's composer now refuses to put a lowering in a reply with anything else.
- A relay-bot post sets no expiry: `expires_at` stays null in an alert and is never in a reply (the composer refuses it). Every released reader stops showing an alert at that time and takes no renewal from the bot, so an expiry in the block would end true alerts on old CLIs. The design's expiry will be computed from the claim.
- The trust root can name the oldest release that reads the feed in full: `min_cli`, an optional key of the checkpoint key certificate (`scripts/sign-checkpoint-key.py --min-cli N.N.N`). A CLI older than it prints one `upgrade:` line after every command that reads the feed and keeps working; `run --json` gains the key `min_cli`. It is in the certificate and not in the manifest, where the design had put it, because of the second fact above. No certificate carries it yet. The 0.1.7 release and earlier ignore the key and never print the line; it speaks to the next release and later ones.

Expiry is computed by the reader and judged by the signed checkpoint, not by the member's clock (design review of 2026-11-23, finding D5, ai-tools-alerts#r0ra). Before, an alert with `expires_at` ended when the machine's clock passed it: a frozen mirror ended it with no key, a clock set ahead ended it at once, and the relay-bot key could post an alert that expired one second later. Now:

- A relay-bot alert's `expires_at` is not read. Only a curator's ends a thread.
- An alert whose first post carries a claim stands for the days `spec/ruleset.json` gives its level after the claim's `confirmed_at` (critical 14, high 30, notice 90). A later claim on the thread renews it. A check that could not confirm holds the level up to 45 days from the last confirmation. When a level's days run out the alert shows at the next level down that still stands (a critical is high until day 30 and notice until day 90), and then it is gone. The longest claim counts; a short one shortens nothing, and a reply that sets a level counts from its own date.
- The clock for all of this is the issue time of the newest checkpoint the CLI holds, and an alert decays only under a checkpoint that lists it. A frozen mirror, a mirror that withholds a renewal (already refused as `mirror incomplete`) and a wrong clock expire nothing; the stale warning says why.
- A pull no longer ages stored alerts out by the machine's clock when it holds a checkpoint: a clock a year ahead used to delete every stored alert older than 35 days.
- A relay-bot alert whose first post has no claim does not expire. That is every relay-bot alert on the feed today: the poster sends no claim yet (ai-tools-alerts#gtw9). A curator's alert with `expires_at` still ends, now by the checkpoint's time: it stays while the CLI holds no checkpoint past that time that lists it.

Not done: the issue asked that an event dated after the checkpoint that lists it be refused. The poster's own checkpoint lists the posts of its run, which are dated after it, so the CLI does not judge an alert's expiry while one of its claims is dated after the checkpoint; the next checkpoint judges it.

The poster sends no claim yet (ai-tools-alerts#3qyq). The one new event it sends is the level-only lowering described above. The relay was checked before this release: it stores and returns a 2048-byte claim tag, and the mirror exporter copies it, byte for byte (ai-tools-alerts#yw7r).

## 0.1.7 — 2026-11-24

The relay bot posts an alert once, when it is complete, and only while it is news (ai-tools-alerts#0dvh, rebuilt on the authoritative-source rule by ai-tools-alerts#dmmf). A high whose vendor page states neither a fixed version nor an affected range waits up to six hours from first sight for one, and then posts with what is known; a critical and a known-exploited entry never wait. An advisory whose primary source was published more than seven days before the poster first saw it goes to the digest's Notice section, never to a real-time root, unless CISA has just listed it as exploited. The block carries the severity word the vendor's page states (never a collector's), a reply carries a changed severity only when it changes something else too, and a range the schema cannot express makes the post say "affected versions: see the source" instead of "versions not stated". Titles and headlines name the public id (`CVE-2026-103435`), while the block id stays the thread key, so installed readers keep matching threads. The mirror page lists a critical once, not once per channel. The state file gains a `waiting` key. A rollback removes the hold and the age limit only and keeps the new titles and severity handling, which threads already posted need.

A reply from the relay bot can no longer take an alert away from members (design review of 2026-11-23, finding D1, ai-tools-alerts#tyje). The CLI already refused a bot reply that lowered an alert's level or set an expiry. It still applied one that lowered `fixed` to `0.0.1`, replaced `products` with a product nobody runs, emptied `actions` or replaced `sources`: the first two remove the alert from every member's `check` while the thread still reads critical, so whoever held the bot's key could silence any bot alert with one signature. Now the `products`, `actions` and `sources` of a reply from a key that is not a curator's are joined to the thread's, never put in their place. The reply may add a product, widen `affected`, raise or clear `fixed`, add an action, raise an upgrade's version, add a source. A product it leaves out stays; a narrower `affected`, a lower `fixed`, a `fixed` where there was none, a weaker action or a missing source changes nothing; the rest of the reply applies. The result is the same in whatever order a thread's replies are read, so a reply dated before an earlier one cannot undo it. The same rule governs the mirror page and the Atom feeds, which are built by the same code. A curator's reply is unchanged: it replaces fields whole.

What the bot's key can still do to its own alert: add entries, add a source (a new source on a primary domain is shown before an older one that is not), and clear `fixed`, after which the member is told to upgrade with no version and only a curator can name one again. Consequences of the rule: a true narrowing from the bot is left out like a forged one: when a vendor publishes a fix for an alert that had no fixed version, members at or above that version keep seeing the alert until a curator signs the change (the member's own check against the source, ai-tools-alerts#h29n, will lift this). A bot reply that changes an entry into one neither wider nor narrower adds it beside the first, so a thread can list a product twice and a member can match both; `curator amend --fixed NAME=VERSION` now sets every entry of that product, and `curator amend` works on a thread whose lists the bot has grown past the schema's limits. Nothing tells a member or a curator yet that a narrowing was left out (ai-tools-alerts#2wa6). And readers at 0.1.6 and earlier still apply a narrowing reply whole; they are protected only once they install 0.1.7 or later. No wire format changes: the advisory block, the events and the poster are as before.

## 0.1.6 — 2026-11-24

The feed checkpoint is in force. `trust/checkpoint-key.json` is the root-signed certificate for the poster's checkpoint key (signed 2026-11-23, expires 2027-03-23), and readers of this release refuse a pull until they hold a valid certificate (this one is bundled, and the mirror serves it) and the mirror serves a checkpoint signed by the key it names.

The CLI accepts an event only when it is a kind 9 message with one `h` tag naming an alert channel in `spec/channels.json`. Before, anything a poster's key had ever signed, anywhere, could be served by the mirror as an alert, a patch or a retraction (security review of 2026-11-23, finding M3). It also refuses a new event dated more than 10 minutes ahead of the local clock: one event dated years ahead used to count as fresh news for years and silenced the warning about a frozen mirror (finding H2). Events already stored are kept whatever their date, so a clock that jumps back cannot undo a stored retraction; they only stop counting as fresh news. The pull summary counts both as `not-channel-post` and `future-dated`. The mirror exporter publishes neither kind of event, which protects installed v0.1.4 readers from the future-dated one.

The CLI now checks that the feed is complete, not only that each post is signed (security review of 2026-11-23, finding H2). Every pull also fetches a certificate from the trust root naming the checkpoint key, and a checkpoint from that key listing the posts that exist. A new post is admitted only when a checkpoint lists it; a mirror that lacks a listed post is refused (`mirror incomplete`); an older checkpoint or certificate is refused; a post the CLI has applied stays applied, so no checkpoint can take a retraction away. The manifest and the certificate are also fetched from a second origin (this repository; `second_origin` in `config.toml`), and the higher manifest wins. `stale_since` now means no fresh checkpoint, in place of the 3-day and 90-day rules. A new state `unverified` (in `check`, `plan` and `run --json`) says why the CLI cannot vouch for completeness: the last pull failed, no fresh checkpoint, an expired certificate. While it holds, `plan` lists nothing under auto-apply. The session-start hook's second line now reads "stale or unverified"; a hook copied from an earlier release still fires, because `stale_since` is non-null in every unverified state. This CLI must not be released before the mirror serves the two new files: until then every pull ends `no checkpoint key certificate`.

The fleet side of the checkpoint: the poster signs one at the end of every run with a key that stays on its own machine (`checkpoint_key_file`, `aitools-alerts-poster checkpoint-keygen`), listing the posts on the mirror and every post the relay acknowledged until the mirror shows it; the relay VM gains one guarded command that only stores it (`ops/vm/mirror-put`); the mirror exporter publishes the certificate and the checkpoint only after verifying them, and the checkpoint only together with every post it lists (`--checkpoint-key`, `--inbox`). None of it is active until the poster's config and the VM are set up (`ops/vm/README.md`).

Two signed documents are defined for that (`aitools_alerts/checkpoint.py`): a certificate, signed by the trust root, naming the one key that may sign feed checkpoints, and the checkpoint itself, which lists the events that exist so that a mirror cannot leave one out unnoticed (security review of 2026-11-23, finding H2). `scripts/sign-checkpoint-key.py` signs the certificate. Installed readers (0.1.5 and earlier) never fetch them.

The relay bot signs only what an authoritative source states (security finding H4 of the 2026-11-23 review, ai-tools-alerts#h340). Before this, anyone could publish an advisory for a package of their own named `claude-code-router`, and the bot would post "upgrade Claude Code to 99.0.0 or later": the product was matched by words in free text, a high needed no source, and the version, title and ids came from the upstream record. Now a product is matched only by exact identity (`spec/scope.json` version 5: names, repository slugs, package keys such as `npm:@anthropic-ai/claude-code`, and CISA KEV vendor and product pairs); a candidate posts at any level only when the CISA KEV catalog or a page of the product's own vendor confirms it; and the ids, fixed version, affected range, title and severity word of a post are read by the poster from that page. Posts name CVE and GHSA ids only and list only the page that confirmed them. An advisory a vendor publishes on its own site only, with no repository advisory, posts as a digest notice. Fewer advisories post: one whose only source is the global GitHub advisory database, NVD, a distribution tracker or news does not. The advisory block is unchanged, so every released reader parses the new posts. Poster-side only; no change to the member CLI. On its first run the new poster discards unsent posts, held notices and deferred candidates composed under the old rules, and says so on stderr.

The poster signs every post on the poster machine and sends it to the relay over HTTPS (`POST /events` with a NIP-98 header); it no longer sends through an ssh wrapper on the relay VM, and the relay VM keeps no key that may post. Before this, whoever took the relay VM could read the bot's key and sign alerts members' CLIs accept (adversarial review finding H1, ai-tools-alerts#vzc3). The poster config drops `relay_send_wrapper` and takes `relay_key_secret` (and `relay_url`, defaulting to the relay); `secrets_helper` is now required to run. `relay_ssh_host` now names only the feed checkpoint's put-only route, and goes with `checkpoint_key_file` and `relay_put_wrapper`; the guard on the VM allows `mirror-put checkpoint` alone. `ops/vm/scan-for-poster-keys.py` checks a machine for any poster key, in files and nested archives, by public key.

## 0.1.5 — 2026-11-23

The install path is pinned to a commit. The README and the Quick install prompt name the release tag and its 40-character commit, and both checks (`git tag -v` against `trust/allowed_signers`, and `git rev-parse <tag>^{commit}` compared with that commit) come before any install command; a failed check means install nothing. The README on the default branch pins the latest release; the README inside a release pins the one before it, since a commit cannot name its own hash. The mirror page's install line follows the README's.

The build backend is pinned to `setuptools==80.9.0`. `ops/vm/README.md` takes every file it installs on the relay VM from one export of the verified release, never from a checkout or a branch. `SECURITY.md` asks for reports through GitHub's private vulnerability reporting, and `.github/CODEOWNERS` names the owner of the trust, spec, ops, hook, skill and snippet files. `scripts/public-scan.sh` also scans history: every object reachable from every ref, commit messages and identities included.

An alert whose source names no fixed version no longer says that no fix is published. CISA's Known Exploited Vulnerabilities catalogue carries no version data, so on 2026-11-10 the Chromium and OpenSSH alerts said "no fix is published yet" while both vendors had shipped one. Such an alert now says the source does not state a fixed version, tells the reader to check the vendor for an update, and, for a known-exploited item, to update now if a release is out; the Japanese twin and the digest line say the same. A curator post with no fixed version says "No fixed version stated." The "Fixed in" wording and the wording for a fix the schema cannot express are unchanged.
