# The poster lowers a level only on evidence held for 24 hours (ai-tools-alerts#ny5g)

Findings D4, D13 and D15 of the design review on ai-tools-alerts#h29n; rules 3 and 6 of its revised design. Slice A of h29n, first half. The second half is ai-tools-alerts#3qyq.

## Problem

The ruling of 2026-11-23 removes the human: the relay bot now lowers a level when its sources no longer support it. Built naively, "recompute every run and post the result" lowers on absence of evidence. One empty answer from CISA reads as "no CVE is exploited" and lowers every critical in a single run. A catalog cut in half does the same for half of them. An author who toggles an advisory makes the bot post on every toggle.

Today the poster never lowers (`main.plan_known`: "a run never lowers a level; a curator does"), and it has no recompute: a thread's level changes only when a new candidate for it arrives. `inputs.fetch_kev` already tells an unavailable catalog from a read one; nothing downstream uses the difference to decide a level.

Prior work read: the design review and revised design (comments on h29n), the v2 design (first comment on ai-tools-alerts#9mx8), the notes left on ny5g by tyje, t8jr and s6mt, `spec/wire.md`, `spec/ruleset.json`. `kata search` for "lower positive evidence 24 hours KEV catalogVersion" and "GHSA OSV advisory API reading withdrawn state poster" finds only ny5g, fv4g and h29n.

## Scope of this slice

The poster has one structured source today, the KEV catalog. This slice builds the rules for when a level may fall and applies them through that one reader. The readers for `api.github.com/advisories/<id>` and `api.osv.dev/v1/vulns/<id>`, the reversible `withdrawn` state (which needs the reader, `pull.py`, to know it) and the claim tag on sent events are ai-tools-alerts#3qyq.

Assumes: the member's reader does not apply a relay-bot lowering yet (`pull._apply_patch` refuses it; the CLI's source check, ai-tools-alerts#fv4g, reports and changes nothing, and applying its result is ai-tools-alerts#tavj). So a lowering sent by this slice changes the poster's ledger and digest and is on the wire for tavj; a member's CLI keeps the higher level until then. That is the safe side and is what spec/wire.md states for released readers.

## Success criteria

1. **Three results.** Every read of a source, per thread, is `confirmed`, `contradicted` or `unknown`. There is no KEV copy at all when the fetch failed (timeout, any status but 200 or 304, a body that does not parse, a body over the size cap, a catalog without the CISA shape) and when the run read a synthetic `--kev-file`. A copy is not complete when it was reached through a redirect (the real fetch follows one so that new entries are still seen, and marks the answer; a 304 that came through a redirect is marked the same way, and a direct 304 stands for whatever body the cache holds, so the state keeps the digest of the last body that came direct and a cached body counts as direct only when it is that body), when its `catalogVersion` is not numbers that order (CISA writes the date, `2026.11.24`) or is older than the latest complete copy's (an old catalog served again says nothing about now), when its `count` is not its number of entries, and when it has fewer entries than 98% of the largest complete copy the poster has ever read. What an incomplete copy lists still counts as listed; what it lacks proves nothing. `unknown` changes no level, starts no wait and adds no time to one.
2. **Every source must answer.** A thread is lowered only when every source its ids are looked up in (`ruleset.source_of` over the thread's bare ids) was read whole in this run. A GHSA or OSV id has no reader in this slice: its read is `unknown`, and a thread carrying one is not lowered. A CVE that the catalog lists under a name that is not the thread's product is `unknown`, not gone.
3. **Held 24 hours.** A lowering needs the same lower level held for 24 hours. Time is added only from one complete read to the next one, and only when the two are at most two hours apart with no unknown read of the thread between them. An unknown read adds nothing and neither does the stretch from it to the next complete read; a gap in which the poster did not run adds nothing. What was already held is kept. Every thread is judged, and what that does to its wait is saved, before anything is sent, so a run that stops at a failed send has still recorded what it read: an unknown read has broken the wait and another level has started it over. The read that completes the wait must be of a later `catalogVersion` than the one that began it. A complete read that gives any other level starts over, and so does any copy, complete or not, that lists the entry at a level that holds the thread's: evidence for a level needs no completeness. A run writes that it has begun observing before it reads anything and clears that when its observation is saved; a run that finds the mark set (the one before stopped in between, or could not write) gives every wait nothing for the stretch up to its own read.
4. **Gone needs seen, per CVE.** The absence of one of the thread's CVEs from a complete copy counts only when a complete copy listed that CVE for the thread's product earlier, as this state file recorded per thread and CVE. A CVE of the thread that the poster never saw listed, a lost state file, an alias learned later: its absence is `unknown`, and the thread is not lowered.
5. **Raises at once.** A recompute that finds a higher level than the thread's publishes in the run that sees it, from any copy that parses, complete or not.
6. **Seven quiet days.** A thread is lowered only when it has had no level change in the last seven days. So no seven-day window holds more than three level changes on one thread (one lowering, then at most two raises), no raise is ever held back, and a source that flaps leaves the thread at its higher level.
7. **Circuit breaker.** A run in which more than two threads and more than 20% of the threads it judges are due to be lowered, counting those lowered in the last 24 hours with those due now (so entries shed a few an hour trip it as entries shed at once do), lowers none (the share is of the threads that can be lowered, so a ledger full of other threads does not make a mass lowering look small), and the next digest carries one fixed line saying so. After seven days tripped without a break, each run lowers two threads, oldest first.
8. **How a lowering is sent.** `compose.level_post`, alone, in every channel the thread has a root; no Japanese copy. The ledger marks the thread `lowered`. On a lowered thread every later level change, from the recompute or from a candidate, is a `level_post` of its own, and any other change of the same run rides a second reply with no level in it (spec/wire.md rule 2).
9. **Never replayed on old evidence.** A journaled lowering that no channel has received is removed before the journal drains, and the run's own recompute sends it again only if a complete read still supports it. One that a channel already has is delivered to the thread's other channel whatever the next read says: the channels must agree. "Has" is judged over the whole change: any of its items the relay acknowledged (journaled as sent, though the ledger may not record it yet) or whose outcome is unknown keeps all of them.
10. **The floor.** A reading of prose never justifies a lowering. The ledger keeps, per thread, the highest level readings of prose alone gave it (`floor`), set when the root is planned and raised by later candidates. The recompute never goes below it. An entry written before this change has none; it is taken to rest on a reading as far as a reading reaches (its own level, or `reading_cap` when that is lower), so an old critical is lowered to high at the lowest. `notice` is the lowest result in any case.
11. **The exploited mark does not raise a lowered thread.** On a thread marked `lowered`, a candidate's `exploited` flag counts only when a KEV entry read this run stands behind it (a `kev` reading). `Run.one` drops the flag otherwise, after the journal has drained, so a flag lent by `ledger.merge` from a ledger not yet reconciled, or kept in the state file with a deferred candidate, raises nothing. `ledger.merge` also stops lending it from an entry marked `lowered`.
12. **One digest line.** The next digest lists the ids lowered since the last digest in one line (D15), once: the digest's date is written to the recompute state before the digest is journaled and the list is emptied after, and a run that stopped between the two files is settled by the next one (the list goes if that date's digest was journaled or sent, and stays if not). That covers the first run after this lands: the first day lowers nothing, and the lowerings that follow are reported the same way.
13. **No retract.** The poster composes no `retract`; a test holds that.
14. **Acceptance cases, each a test through `main.run` with one run an hour:** an empty KEV body, a 404, a 429, a 503, a KEV catalog missing half its entries, one with no version and one that disagrees with its count each lower nothing over 30 hours and begin no wait; an outage in the middle of a wait adds no time to it, one unknown read at 22 hours held delays the lowering by its two hours, complete reads that alternate with unknown ones never add up, and a poster that did not run for 38 hours gets nothing for them; a thread with two CVEs of which only one was ever listed is not lowered when both are absent, until the other has been seen; a whole catalog reached through a redirect lowers nothing, and a cached body is direct only when it is the body that came direct; an unknown read in a run that stops at a failed send still breaks the wait, whether the whole catalog was unreadable or only this thread's entry was (listed under another name), and a read that lists the entry in such a run starts the wait over; entries shed one an hour trip the breaker; a lowering acknowledged by one channel whose ledger write failed reaches the other channel in the next run, and a candidate merged in that run is raised to what its page supports, not to critical; a digest report interrupted on either side of the journal write is listed exactly once; three KEV threads due beside twenty other threads trip the breaker; a lowered thread listed again in a catalog that disagrees with its count is still raised in that run, and such a catalog listing the entry at 22 hours held ends the wait; two older catalogs served in turn after the entry was listed lower nothing; a run that stopped before saving what it read gives the next read no time; a vendor candidate arriving on the run a lowering falls due (a GHSA id, a fix, a floor of high) is seen first: nothing is lowered and the fix is in the ledger; a lowering finished from the journal in a run whose catalog lists the entry again is followed by the raise in that run; a redirect that ends in 304 is not a complete read; a later candidate with a fix on a lowered thread raises it to what its page supports and not to critical; a floor of high set by the vendor's page survives new runs and a later candidate without a severity, and an entry written without a floor is lowered to high and no further; a KEV entry gone for a day of complete reads lowers once and not again; the same with one unchanged `catalogVersion` does not; a KEV entry that toggles hourly moves nothing, and one that leaves and returns every two days gives at most three level changes in any seven days, every raise in the first run that lists it; a lowering whose send failed is not sent in a later run that cannot read KEV; a lowering one channel has reaches the other; after a lost state file absence lowers nothing until the entry has been seen again; the OpenSSH thread CVE-2026-123158, replayed from the live feed's root as the ledger holds it (critical, both channels, no floor), is lowered once to high after a day of complete reads and stays there, with no human. (Written against ruleset version 1, under which CISA's listing kept it critical and the lowering waited for ai-tools-alerts#9kgk. Scope version 6 and ruleset version 2, merged from main during this work by ai-tools-alerts#wa6n, put OpenSSH outside the channel class, where a KEV entry supports a notice; the old entry's floor is high.)
15. `scripts/test-gate.sh` passes.

## Approach

### A new module, `aitools_alerts/poster/recompute.py`

Pure rules and one small state file. It imports `ruleset`; it sends and fetches nothing.

**The KEV copy.** `kev_copy(catalog, status, st, now)` returns `Copy(version, index by cveID, complete)`, or None when there is nothing to use (criterion 1). `complete` needs a version, `count == len(entries)` with no cveID twice, and at least 98% of the peak. The peak is the largest complete copy this state has read and never falls: a run of small copies, however long, never becomes the measure, and a 1% loss a day does not add up. If CISA ever prunes more than 2% of the catalog the poster stops lowering on KEV absences and says so on stderr each run; it still raises. That is the safe side of a rule the issue fixes at 2%.

**A thread's support.** `support(entry, scope, copy, rs)` returns `(found, known, listed)`:
- The thread's bare ids are the CVE and GHSA ids of its published advisory and of the ledger's identity set; an id of any other shape makes `known` false.
- For each CVE id the copy lists: the reading `{cve_id, name}` (`vendorProject` and `product`, each trimmed, joined by one space; s6mt note 3), and `rs.read("kev", fields)` gives what it supports for the thread's product. No support for this product (another name, a name the canonical form cannot carry) makes `known` false.
- Any id whose source is not `kev` makes `known` false (no reader).
- `known` also needs a complete copy.

Only a thread the ledger marks `exploited` is recomputed: that mark is set only from a KEV entry (`candidates.from_kev`), so those are the threads whose level rests on the catalog. A synthetic thread, a thread whose product no scope entry names, and a thread kept under a product's former name (scope `formerly`, wa6n) are skipped: not judged, never lowered.

**The decision, per thread** (`judge`):
- `found` above the thread's level: a raise, now; its wait is dropped.
- `known`: the CVEs listed for this product are added to `st["listed"][root]`.
- the level is the highest of `found`, the floor and `notice`. Not below the thread's: the wait is dropped, whether or not the read is `known`.
- not `known`, or a CVE is gone that `st["listed"][root]` does not hold (criterion 4): nothing moves. A wait already running keeps `held` and has its `last` cleared, so the stretch up to the next complete read adds nothing.
- below: a wait `{level, version, last, held}` begins with `held` 0, or, when one for the same level runs, gains `now - last` if `last` is set and at most two hours back; `last` becomes `now`. It is due when `held >= 24 h` and the copy's version is later than the wait's.

`Run.recompute` judges every open exploited thread in every run, with or without a copy, so that a run with no copy clears `last` on every wait.

**The state**, `<ledger>.recompute.json` beside the ledger, written atomically under the ledger lock: the peak and last complete version; per root, the CVEs a complete copy has listed for its product; the waits by root; the ids lowered since the last digest; since when the breaker has been tripped and how many threads were due. It is not in the run journal, so the journal's strict key check is untouched. A file that does not read is replaced by an empty one and the run says so on stderr: every wait starts over and no absence counts until the entry is seen again, which can only delay a lowering.

### In `main.run`

Before the journal drains, `Run.observe(kev_out)`:
1. Settle an interrupted digest report; judge the copy (`kev_copy`).
2. `drop_unsent_lowerings()` (criterion 9), first, so that what it removes no longer makes its thread busy.
3. Judge every open exploited thread (`judge`), which is all the bookkeeping of the waits. A thread with journaled work or a send in flight (`Run.busy`) is not judged and its wait is paused. Save the state.

After the candidates are planned and before the digest, `Run.recompute()` sends what the verdicts say:
1. Judge the threads this run posted (they were not there before; this records that a complete copy lists them).
2. Judge again, from the entry as it is now, every thread that was busy at the start (the drain may have finished its work, and a catalog that lists it again must raise it in this run) and every thread whose ledger entry is no longer the one its verdict was reached on (a candidate of this run added an id, a floor, a fix or another level). No verdict outlives its entry, and the reply is composed from the current advisory.
3. Of the due threads, keep those with no level change in the last seven days (`Entry.changed`) and pass them through the breaker (`select`).
4. Enqueue every raise, then every lowering the breaker let through. A wait is not dropped when its lowering is enqueued: it goes when the ledger shows the level.

`gather` hands the catalog it read to the run through an optional `kev_out` dict, so its three return values stay as tests patch them.

A level change is a journal item of kind `reply` with its own key (`<id>#level`), whose advisory is the thread's with the new level. It is sent and recorded as a reply is. `Ledger.record_reply` sees the level differ and appends the time to the entry's `changed` list (kept for seven days) and sets `lowered` when the level fell; the second channel's copy of the same change finds the level equal and counts nothing twice. When a lowering is recorded, its id joins the "lowered since the last digest" list.

`Run.one` computes the candidate's prose floor (`rules._prose_level` with the exploited flag off). A new root's item carries it to `Ledger.record_root`; for a known thread `Ledger.learn_floor` keeps the highest of it and what the thread had.

`plan_known`, on a thread marked `lowered`, takes the level out of the reply's changes and puts a `level_post` item before it; the reply is composed against the thread with the new level and with `lowered=True`, which `compose.reply_post` already enforces.

### The digest

`compose.level_report(lowered, tripped, lang)` returns the extra lines, guarded like every other post text: "Lowered since the last digest: CVE-… to high; …." and, while tripped, "Level check: N threads are due to be lowered at once and are held back." `Run.digest` appends them to both the English and the Japanese digest and empties the list once the digest is journaled.

### Not in this slice, by decision

A send whose outcome is unknown, or that the relay refused, holds every later change to its thread until `resolve` settles it, a raise included. That is how the send journal has worked since the first release, for every thread, and the recompute inherits it. Settling such a send from the mirror without a person, and letting a raise pass unsent lower-priority work, is ai-tools-alerts#jsje; ai-tools-alerts#m729 covers the other direction (events under the poster's key that its ledger did not send). It is not built here.

## Alternatives considered

- **Recompute inside the candidate path.** A thread would be recomputed only when a candidate for it arrives; a KEV entry that leaves produces no candidate. Rejected.
- **Lower on the KEV read alone when a thread also has a GHSA id.** The GitHub advisory may still support the level. Rejected until 3qyq gives it a reader.
- **The literal weekly limit (three changes, then silence).** The fourth change can be a true raise to critical. The seven-quiet-days rule gives the same bound and never holds a raise.
- **A breaker that stays tripped.** It needs a person to clear it. The ruling excludes that.
- **A small KEV copy that becomes the measure after seven days** (the first draft). The spec review refused it: time spent failing must not make an incomplete catalog authoritative. The peak never falls; the cost is stated in the approach.
- **Rebuilding the floor from the published advisory** (the first draft). The published fields hold neither the model flags nor the severity text the prose rules read, so the rebuilt floor could be lower than what the thread rested on. The ledger keeps it.
- **The state inside the journal file.** The journal refuses unknown keys, so an older poster could not load it after a rollback. The translation state set the pattern of a file beside the ledger.
- **`withdrawn` as a level in this slice.** The current reader would refuse the reply as an unknown level and the block schema is frozen for roots; it needs reader work. 3qyq.

## Blast radius and rollback

Poster only: `recompute.py` (new), `main.py`, `ledger.py`, `compose.py`, `inputs.py`. No reader, schema, wire or ruleset file changes. Three ledger entry keys are added, all optional (`lowered`, `changed`, `floor`), and one optional journal item key (`floor`, on a root until it is recorded). `changed` is written by a raise as well as by a lowering, so any of the three can be in a ledger before the first lowering. `inputs.urllib_fetch` gains the redirect mark; the KEV cache file does not change. Until a lowering is due, nothing a member sees changes: the first day only writes the state file and the floors.

Rollback is one-way once a thread is marked `lowered`. An older poster refuses a ledger with keys it does not know, and that refusal is the intended stop: started on a ledger with the keys stripped, it would not know to send a later raise alone, and a reader that kept the higher level would lose a fix sent with it (spec/wire.md rule 2). To go back anyway: stop the poster; in every entry marked `lowered` set `level` and `advisory.level` to the highest level the thread has had; in the state file, remove every `outbox` item and every `withheld` group whose key holds `#level:`, and in every other `outbox` item and `withheld` item whose `root` is such a thread set `adv.level` to that same level (a reply's journal item holds the whole advisory, and recording it would write its level back); remove the `floor` key from every item; remove `lowered`, `changed` and `floor` from every ledger entry; delete `<ledger>.recompute.json`. The old poster then holds what every released reader holds. When no entry is marked `lowered`, the last three steps are enough: the `floor` key off every journal item, the three keys off every ledger entry, the recompute file deleted. A test holds that those are all the keys the 0.1.7 poster does not know. The changelog carries this.

## Open questions

- Whether a recompute raise to critical on a thread that has no root in the critical channel should post a copy there. It cannot happen under ruleset version 1 (a KEV thread of a tier-1 product is posted critical, in both channels). Left for 9kgk, which changes the rule.
- A thread kept under a former product name is not recomputed. `Ruleset.level` reads such names; `rules.scope_of` does not resolve them. Left for 3qyq, which touches the same lookup.
